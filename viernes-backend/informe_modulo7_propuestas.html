Estado actual del proyecto

El CRM Viernes V1 es una aplicación Spring Boot 4.0.7 con Java 21, Oracle XE (FREEPDB1), Spring Modulith, Lombok, MapStruct y Springdoc OpenAPI. Usa hibernate.ddl-auto: update para el esquema de BD.

Propósito del módulo

El pipeline de oportunidades (PROSPECCION → CONTACTO → CALIFICACION → PROPUESTA → NEGOCIACION → GANADA → PERDIDA) ya incluye la etapa PROPUESTA en el enum EtapaOportunidad, lo que confirma que el flujo comercial esperaba este módulo.

El módulo representa una propuesta comercial formal asociada a una oportunidad: un documento que detalla productos/servicios ofertados, cantidades, precios unitarios y un monto total, con un flujo de estados que refleja el proceso de negociación.

  • Relación obligatoria con una oportunidad existente.
  • Cliente derivado de la oportunidad o especificado explícitamente.
  • Múltiples líneas de detalle (productos/servicios).
  • Flujo de vida controlado con estados.

DDL de referencia — Oracle XE

CREATE TABLE CRM_PROPUESTAS (
    ID               NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    NUMERO_PROPUESTA VARCHAR2(50)    NOT NULL UNIQUE,
    ID_OPORTUNIDAD   NUMBER(19)      NOT NULL,
    ID_CLIENTE       NUMBER(19)      NOT NULL,
    CLIENTE_NOMBRE   VARCHAR2(150),
    ESTADO           VARCHAR2(20)    NOT NULL,
    VERSION          NUMBER(5)       DEFAULT 1 NOT NULL,
    SUBTOTAL         NUMBER(14,2)    NOT NULL,
    DESCUENTO        NUMBER(14,2)    DEFAULT 0 NOT NULL,
    TOTAL            NUMBER(14,2)    NOT NULL,
    RESPONSABLE      VARCHAR2(100),
    FECHA_EMISION    DATE            NOT NULL,
    FECHA_VENCIMIENTO DATE,
    OBSERVACIONES    CLOB,
    CREADO_EN        TIMESTAMP       NOT NULL
);

CREATE TABLE CRM_PROPUESTA_DETALLES (
    ID               NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ID_PROPUESTA     NUMBER(19)      NOT NULL,
    DESCRIPCION      VARCHAR2(500)   NOT NULL,
    CANTIDAD         NUMBER(10)      NOT NULL,
    PRECIO_UNITARIO  NUMBER(14,2)    NOT NULL,
    SUBTOTAL         NUMBER(14,2)    NOT NULL,
    CONSTRAINT FK_DETALLE_PROPUESTA FOREIGN KEY (ID_PROPUESTA)
        REFERENCES CRM_PROPUESTAS(ID) ON DELETE CASCADE
);

Reglas de negocio

#ReglaVeredicto
R1Una propuesta debe estar asociada a una oportunidad existente✅ Aceptada
R2Una propuesta debe tener un cliente existente✅ Aceptada

R6Montos no pueden ser negativos; cantidad mínima 1✅ Aceptada
R7fechaVencimiento no puede ser anterior a fechaEmision✅ Aceptada
R8Solo se puede ENVIAR una propuesta en estado BORRADOR✅ Aceptada
R9Solo se puede APROBAR o RECHAZAR una propuesta ENVIADA✅ Aceptada
R10Una propuesta CANCELADA no puede volver a estados anteriores✅ Aceptada

Flujo de estados

BORRADOR → ENVIADA → APROBADA
BORRADOR → ENVIADA → RECHAZADA
BORRADOR / ENVIADA → CANCELADA

Riesgos e inconsistencias

1
Sin FK físicas entre módulos — registros huérfanos

Si se elimina una oportunidad o cliente, las propuestas quedarán con IDs inválidos. Mitigación: coherente con la arquitectura actual del proyecto. Las FK lógicas son una decisión deliberada para el desacoplamiento modular.

2
clienteNombre desnormalizado

Puede quedar desactualizado si se cambia el nombre del cliente. Patrón ya existente en OportunidadEntity.clienteNombre. Aceptado como trade-off.

3
responsable es String libre

Sin validación contra un módulo de Usuarios (que aún no existe). Coherente con todos los módulos del sistema.

4
Generación del número de propuesta — race conditions

El formato PROP-YYYY-NNNN generado con SELECT COUNT puede tener colisiones en concurrencia alta. Mitigación: en V1 el tráfico es bajo. En V2 se puede usar una SEQUENCE de Oracle.

5
Inconsistencia en convención de columnas

Actividades usa snake_case, los demás módulos usan MAYUSCULAS. El Módulo 7 sigue la convención mayoritaria: MAYUSCULAS.

18

Decisiones de diseño aprobadas

  • 1
    Estructura de 2 tablas: CRM_PROPUESTAS + CRM_PROPUESTA_DETALLES con relación 1:N.
  • 2
    Estados de propuesta: BORRADOR, ENVIADA, APROBADA, RECHAZADA, CANCELADA.
  • 3
    Relación con oportunidad: referencia lógica por ID_OPORTUNIDAD (Long), sin FK física, obligatoria.
  • 4
    Relación con cliente: referencia lógica por ID_CLIENTE (Long) + CLIENTE_NOMBRE desnormalizado.
  • 5
    FK física solo entre Propuesta → Detalles (ON DELETE CASCADE), al ser del mismo aggregate.
  • 6
    Modelo financiero V1: SUBTOTAL, DESCUENTO, TOTAL. Sin impuestos ni moneda.
  • 7
    Cálculo automático del total: subtotal = Σ(cantidad × precioUnitario), total = subtotal − descuento.
  • 8
    Reglas de transición de estado: BORRADOR→ENVIADA→APROBADA/RECHAZADA, cancelable desde no-terminal.
  • 9
    Inmutabilidad: propuestas en estado APROBADA, RECHAZADA o CANCELADA no se pueden modificar.
  • 10
    Eliminación solo en BORRADOR.
  • 11
    Endpoints REST con PATCH para transiciones de estado.
  • 12
    DTOs como record (4 DTOs: request/response para propuesta y detalle).
  • 13
    Excepción de conflicto de estado en GlobalExceptionHandler con código 409.
  • 14
    Generación automática de numeroPropuesta (formato PROP-YYYY-NNNN).
  • 15
    NO se modifica el Dashboard en esta fase.
  • 16
    Estrategia Oracle XE: GenerationType.IDENTITY, ddl-auto: update.
