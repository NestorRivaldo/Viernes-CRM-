Arquitectura Hexagonal – Visión General

Todos los módulos de negocio comparten la misma estructura hexagonal. El núcleo del dominio (reglas de negocio puras) está completamente aislado de cualquier framework o base de datos. Las dependencias apuntan siempre hacia el dominio, nunca al revés.

🏛️
domain/
Entidades y enums de negocio puras. Sin anotaciones JPA, Spring ni frameworks. Ej: Lead.java, EstadoLead.java.
🔌
application/port/in
Casos de Uso (interfaces). Definen qué puede hacer el sistema. Ej: ManageLeadUseCase.
🔌
application/port/out
Puertos de salida (interfaces). Lo que el sistema necesita del exterior. Ej: LeadPersistencePort.
⚙️
application/service
Servicios de aplicación. Implementan los UseCases orquestando el dominio y los puertos de salida.
🌐
adapters/in/web
Controladores REST. Reciben HTTP e invocan el UseCase. Desconocen la implementación real.
💾
adapters/out/persistence
Adaptadores JPA. Implementan el puerto de salida. Traducen entre Dominio y Entidad @Entity.
ℹ️
Regla de la Dependencia: El código dentro de domain/ y application/ no puede importar clases de adapters/. Spring Modulith refuerza este límite en tiempo de test con ApplicationModuleTest.

Flujo de Trabajo – Crear un Lead

Ejemplo del ciclo de vida completo de una petición HTTP en la nueva arquitectura hexagonal:

1
El frontend envía POST /api/v1/leads con JSON al servidor.
2
LeadController (adaptador web) deserializa el body en un LeadRequest (DTO) y lo valida con Bean Validation.
3
El controlador invoca ManageLeadUseCase.crear(request) — solo conoce la interfaz, no la implementación.
4
LeadService aplica las reglas de negocio: construye un objeto Lead (dominio puro) con estado por defecto NUEVO.
5
El servicio llama a LeadPersistencePort.save(lead) — el dominio no sabe nada de JPA.
6
LeadPersistenceAdapter convierte el Lead en LeadEntity y delega a LeadSpringDataRepository.save(entity).
7
Spring Data JPA / Hibernate persiste el registro en la tabla CRM_LEADS de Oracle XE.
8
El adaptador convierte la entidad guardada de vuelta a Lead (dominio) → el servicio lo convierte a LeadResponse (DTO).
9
El controlador devuelve HTTP 201 Created con el LeadResponse en JSON.

Módulo Shared – Infraestructura Transversal

El paquete com.viernes.shared contiene todo lo que es reutilizable por todos los módulos. No contiene lógica de negocio.

🚨
GlobalExceptionHandler
Intercepta todas las excepciones con @ControllerAdvice. Devuelve respuestas JSON estructuradas con código HTTP adecuado (404, 400, 500).
❌
ResourceNotFoundException
Excepción de dominio lanzada cuando un recurso no existe. Mapea a HTTP 404 Not Found.
🔍
OpenApiConfig
Configura SpringDoc / Swagger UI con la documentación automática de todos los endpoints REST del sistema.
🌍
CorsConfig
Define qué orígenes web pueden hacer peticiones a la API. Configurado en application-dev.yml.
🔎
Filter / Interceptors
Interceptores que se ejecutan antes o después de cada petición para logging de tiempos, seguridad o auditoría.
✅
Buena práctica: Los módulos de negocio pueden importar clases de shared/, pero nunca al revés. El módulo shared debe mantenerse libre de dependencias hacia los módulos de negocio.
⚠️
Atención con Spring Modulith: Las clases del dominio que deben ser visibles entre módulos (como EstadoCliente usada desde dashboard) deben estar declaradas en el nivel raíz del módulo o en un paquete público explícito para que Spring Modulith no bloquee el acceso.

NUEVO MÓDULO

Módulo 5: Actividades y Seguimiento

Este módulo permite registrar y controlar las acciones que realizan los vendedores (llamadas, reuniones, tareas y seguimientos) sobre los clientes, leads u oportunidades. Es la fuente transaccional clave que alimentará las métricas del Dashboard.

🏛️
Dominio (Core)
Entidad: Actividad.
Tipos: LLAMADA, REUNION, TAREA, SEGUIMIENTO.
Estados: PENDIENTE, EN_PROCESO, COMPLETADA, CANCELADA.
⚙️
Reglas de Negocio
Al crear una actividad se valida la fecha, se le asigna estado PENDIENTE por defecto y se estampa la fecha de creación. Orquestado por el ActividadService.
💾
Persistencia
Los datos se almacenan en la tabla CRM_ACTIVIDADES en Oracle XE. Adaptado mediante ActividadPersistenceAdapter y Spring Data JPA.
Endpoints REST - ActividadController 
POST   /api/v1/actividades              // Crea una actividad (con ID de cliente/lead/oportunidad)
GET    /api/v1/actividades/{id}         // Consulta una actividad específica
GET    /api/v1/actividades              // Lista actividades (acepta filtros ?estado, ?idCliente, etc.)
PATCH  /api/v1/actividades/{id}/estado  // Avanza o cancela la actividad
DELETE /api/v1/actividades/{id}         // Elimina la actividad

Informe 3.2: Uso de los Módulos (Backend API)

Para interactuar con el backend de VIERNES CRM, cada módulo expone una serie de endpoints RESTful a través de sus controladores web. La comunicación se realiza mediante JSON bajo la ruta base /api/v1/.

Módulo Operación Método y Ruta REST Descripción
Clientes Crear POST /api/v1/clientes Registra un nuevo cliente en el sistema.
Obtener todos GET /api/v1/clientes Lista todos los clientes registrados.
Obtener por ID GET /api/v1/clientes/{id} Recupera los detalles de un cliente específico.
Actualizar PUT /api/v1/clientes/{id} Actualiza los datos completos de un cliente.
Desactivar PATCH /api/v1/clientes/{id}/desactivar Cambia el estado del cliente (ej. Inactivo) sin borrarlo.
Eliminar DELETE /api/v1/clientes/{id} Elimina permanentemente al cliente de la base de datos.
Leads Crear POST /api/v1/leads Registra un nuevo lead (prospecto).
Obtener todos GET /api/v1/leads Lista los leads con filtros opcionales.
Obtener por ID GET /api/v1/leads/{id} Recupera un lead específico.
Actualizar PUT /api/v1/leads/{id} Actualiza la información de contacto del lead.
Cambiar Estado PATCH /api/v1/leads/{id}/estado Avanza o rechaza el lead (ej. a "Contactado" o "Perdido").
Eliminar DELETE /api/v1/leads/{id} Elimina el lead del sistema.
Oportunidades Crear POST /api/v1/oportunidades Inicia una nueva oportunidad de venta.
Obtener todas GET /api/v1/oportunidades Lista el pipeline de ventas.
Obtener por ID GET /api/v1/oportunidades/{id} Recupera una oportunidad en específico.
Actualizar PUT /api/v1/oportunidades/{id} Modifica el monto o detalles de la oportunidad.
Cambiar Etapa PATCH /api/v1/oportunidades/{id}/etapa Mueve la oportunidad en el embudo (Pipeline).
Eliminar DELETE /api/v1/oportunidades/{id} Elimina la oportunidad.
💡
Cómo probar la API: Puedes probar todos estos endpoints de forma interactiva y ver los esquemas JSON requeridos ingresando a http://localhost:8080/swagger-ui.html mientras el proyecto está en ejecución.

Informe: Activación del Proyecto

Para levantar y activar el proyecto VIERNES CRM en cualquier PC, sigue estos pasos secuenciales. Asegúrate de cumplir con los requisitos previos antes de iniciar.

1. Requisitos Previos

☕
Java 21
Tener instalado el JDK 21. Verifica con java -version.
🐳
Docker
Tener Docker y Docker Compose instalados y en ejecución para la base de datos Oracle XE.

2. Pasos de Activación

1
Levantar Base de Datos
Abre una terminal en la raíz del proyecto y ejecuta el siguiente comando para levantar el contenedor de Oracle XE en segundo plano:
docker-compose -f compose-dev.yml up -d
2
Iniciar el Backend (Spring Boot)
En la terminal, ejecuta el proyecto usando el Wrapper de Maven:
En Windows: .\mvnw.cmd spring-boot:run
En Linux/Mac: ./mvnw spring-boot:run
3
Verificar Ejecución
Una vez que la consola muestre que la aplicación ha iniciado, puedes probar la API ingresando a la interfaz de Swagger UI:
http://localhost:8080/swagger-ui.html
