Informe Final Módulo 6: Dashboard y Métricas

Documentación técnica y funcional del orquestador de KPIs estadísticos del CRM.

ESTADO: LISTO (V1)

1. Propósito y Alcance

El Módulo 6 proporciona una visión agregada y estadística de los módulos de Clientes, Leads, Oportunidades y Actividades. Funciona de manera pasiva y optimizada: no crea tablas nuevas, ni modifica los datos existentes, sino que los lee mediante consultas JPQL eficientes para construir indicadores comerciales (KPIs).

Responde a la pregunta: ¿Cuál es el estado general del negocio en tiempo real?

2. Implementaciones Realizadas (Lógica de Módulo)

  • Separación por DTOs: Se crearon DTOs anidados y estructuras de respuesta (`DashboardResumenResponse`, `EstadoCantidadResponse`, etc.) garantizando que las Entidades JPA jamás lleguen al Controller.
  • Lectura Pasiva: No se han añadido entidades al contexto. Se delegó en `DashboardQueryRepository` inyectando `EntityManager` para realizar consultas de agregación a las tablas nativas de Oracle XE (`CRM_CLIENTES`, `CRM_OPORTUNIDADES`, etc.).
  • Cálculos Agrupados: Las operaciones matemáticas (Pipeline, Valor ganado, Cantidad por Etapa) se ejecutan mediante JPQL (ej. `SUM(o.valor)`, `COUNT(l)`), permitiendo una respuesta rápida sin cargar el servidor de Java con grandes cantidades de datos.
  • Manejo de Dinero y Nulos: Los cálculos monetarios emplean estrictamente `BigDecimal`. Se han manejado apropiadamente los valores vacíos, retornando `0` si la base de datos está vacía.
  • Testing Completo: Se incluyeron `DashboardServiceTest` y `DashboardControllerTest` (usando Mockito y MockMvc), validando las métricas en escenarios vacíos y poblados, asegurando que el módulo compile y pase las pruebas unitarias satisfactoriamente.

3. Endpoints de la API

Los endpoints exponen información consolidada y siguen el principio del mínimo acoplamiento en la Arquitectura Hexagonal:

GET    /api/v1/dashboard/resumen        # Consolidado general (Devuelve todos los bloques)
GET    /api/v1/dashboard/kpis           # Totales y conversiones (Clientes, Leads, Oportunidades)
GET    /api/v1/dashboard/pipeline       # Totales de ventas, Oportunidades por Etapa y valor financiero
GET    /api/v1/dashboard/leads          # Cantidad de leads y agrupación por estado
GET    /api/v1/dashboard/actividades    # Cantidad de actividades y agrupación por tipo y estado

4. Arquitectura y Persistencia

Apegado estrictamente al marco de Spring Modulith y a la estructura Hexagonal. Las consultas directas de lectura evitan romper el aislamiento de dominios. Todos los datos provienen de Oracle XE.

com.viernes.dashboard/
├── application/
│   ├── dto/                 # DashboardResumenResponse, TipoCantidadResponse, etc.
│   ├── port/in/             # DashboardUseCase
│   ├── port/out/            # DashboardPersistencePort
│   └── service/             # DashboardService (orquesta las peticiones)
└── adapters/
    ├── in/web/              # DashboardController (Controlador REST)
    └── out/persistence/     # DashboardPersistenceAdapter y DashboardQueryRepository

5. Próximos Pasos (Limitaciones Actuales)

De acuerdo con la directiva de no sobre-diseñar (V1), se han documentado las siguientes oportunidades de mejora para el futuro:

  • Filtros Temporales: No se implementaron en esta fase. A futuro, se podrían agregar los parámetros ?fechaInicio= y ?fechaFin= en los endpoints para hacer reportes acotados.
  • Agrupación por Responsable: Debido a la ausencia del Módulo de Usuarios, no se agruparon estadísticas por vendedores. Esto será útil al tener la tabla usuarios implementada.
  • Frontend: El backend se encuentra 100% preparado para ser conectado a cualquier cliente JavaScript o HTML para la graficación de los resultados mediante charts (e.g. Chart.js o Recharts).
