Cómo Construir un Módulo desde Cero

Guía paso a paso para crear un módulo completo a mano: dónde empezar, qué copiar de otros módulos, qué adaptar y qué escribir nuevo. Usamos el módulo clinica del examen como ejemplo.

Copiar Adaptar Nuevo Patrón N:M 12 fases
COPIAR Copiar el archivo casi literal de otro módulo
ADAPTAR Copiar la estructura pero cambiar nombres/campos
NUEVO Escribir desde cero, no existe en ningún módulo
🧮
La regla del 80/20: el 80% de un módulo nuevo es copiar y adaptar patrones que ya existen. El 20% que debes escribir desde cero es: (1) el SQL de las tablas, (2) las reglas de validación del service y (3) la lógica de la relación N:M. Si entiendes esas tres cosas, puedes construir cualquier módulo.

□ El panorama: qué vas a construir

Antes de escribir una línea de código, entiende qué piezas necesitas. El módulo clínica tiene 3 entidades y una relación N:M.

PIEZA 1 — Simple
Clínicas (CRUD)

Una tabla, un CRUD. Igual que etiquetas. Aquí aprendes el patrón básico.

PIEZA 2 — Catálogo
Especialidades (solo lectura)

Una tabla que el frontend lee pero no edita. Más simple todavía: solo GET.

PIEZA 3 — Compleja
Consultorios (N:M)

Cabecera + detalles. La parte nueva. Aquí está el NUEVO de verdad.

Orden de construcción: empieza por la pieza más simple (clínicas), luego el catálogo (especialidades), y al final la pieza compleja (consultorios con N:M). Cada pieza te enseña algo que necesitas para la siguiente.

01 Fase 1: Base de datos

Siempre se empieza por la base de datos. Sin tablas, no hay nada que el backend pueda leer ni escribir.

1.1
Escribir el SQL de las tablas
NUEVO
Siempre nuevo Origen: el examen lo da

El SQL es siempre nuevo porque las tablas y columnas son específicas de cada módulo. Nadie lo puede copiar por ti. Pero el patrón sí se repite: cada tabla sigue las mismas convenciones.

-- Patron: CREATE TABLE [ESQUEMA].[TABLA] ( -- ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, -- ... columnas ... -- CONSTRAINTS (unique, check, FK) -- ) CREATE TABLE EXA_CLINICA.CLINICAS ( ID NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, RUC CHAR(11) NOT NULL, RAZON_SOCIAL VARCHAR2(150) NOT NULL, TELEFONO VARCHAR2(20), ACTIVO NUMBER(1) DEFAULT 1 NOT NULL, CONSTRAINT UQ_CLINICA_RUC UNIQUE (RUC), CONSTRAINT CK_CLINICA_ACTIVO CHECK (ACTIVO IN (0, 1)) );
Qué mirar antes de escribir: abre base de datos/03_tablas/07_actividades.sql y mira el patrón: PK con GENERATED BY DEFAULT AS IDENTITY, constraints UQ_ para únicos, CK_ para checks, FK_ para foráneas. Tus tablas deben seguir las mismas convenciones.
La tabla N:M es la única distinta: CONSULTORIO_ESPECIALIDAD tiene PK compuesta (dos columnas que a la vez son FK). No tiene ID propio. Este patrón no aparece en el SQL de actividades (que usa tabla intermedia con ID propio). Cópialo del examen.
1.2
Insertar datos semilla
NUEVO

Los datos iniciales (3 clínicas, 4 consultorios, 5 especialidades) son específicos del examen. Escríbelos en el mismo script.

1.3
Dar permisos al usuario del backend
ADAPTAR

El examen dice GRANT ... TO BOMERP_APP. Tu proyecto usa BOM_VENTAS. Cambia el nombre del usuario. El resto es igual.

-- Examen dice: GRANT SELECT, INSERT, UPDATE, DELETE ON EXA_CLINICA.CLINICAS TO BOMERP_APP; -- Tú cambias a: GRANT SELECT, INSERT, UPDATE, DELETE ON EXA_CLINICA.CLINICAS TO BOM_VENTAS;

02 Fase 2: Esqueleto del paquete

Crear las carpetas y el package-info.java. Es lo más rápido pero si lo olvidas, Spring no encuentra el módulo.

2.1
Crear las carpetas
COPIAR

Crea esta estructura dentro de viernes-backend/src/main/java/com/viernes/clinica/. Es idéntica en todos los módulos:

clinica/ ├─ adapters/ │ ├─ in/web/ ← controllers │ └─ out/persistence/ │ ├─ entity/ ← @Entity JPA │ └─ repository/ ← Spring Data ├─ application/ │ ├─ dto/ ← records Request/Response │ ├─ port/in/ ← interfaces de use case │ ├─ port/out/ ← interfaces de persistencia │ └─ service/ ← lógica de negocio └─ domain/ ← POJOs y enums puros
2.2
Crear package-info.java
ADAPTAR

Copia de cualquier módulo (ej: etiquetas/package-info.java) y cambia el nombre del paquete.

// COPIAR de etiquetas/package-info.java y cambiar: @org.springframework.modulith.ApplicationModule( allowedDependencies = {"shared", "shared.exception"} ) package com.viernes.clinica; ← solo esto cambia
Si el módulo no depende de otros: el clinica es autónomo, solo necesita shared. Si tu módulo necesita leer de clientes, agrega "clientes" en allowedDependencies.

03 Fase 3: Dominio (POJOs + enums)

El dominio son clases POJO puras y enums. Sin JPA, sin Spring. Es lo más fácil de copiar: la estructura es siempre igual, solo cambian los campos.

3.1
Crear el POJO del dominio
ADAPTAR

Copia de etiquetas/domain/Etiqueta.java. Cambia los campos por los de tu entidad. La estructura es idéntica:

// PATRÓN (de Etiqueta.java): @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class Etiqueta { private Long id; private String nombre; private Boolean activa; private LocalDateTime creadoEn; } // ADAPTADO a Clinica.java: @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class Clinica { private Long id; // ← igual private String ruc; // ← cambia el campo private String razonSocial; // ← cambia el campo private String telefono; // ← cambia el campo private Integer activo; // ← cambia el tipo }

Qué NO cambia nunca: las anotaciones de Lombok (@Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder), el campo id de tipo Long, el hecho de que no tiene anotaciones de JPA.

3.2
Crear el enum
ADAPTAR

Copia de productos/domain/EstadoProducto.java. Cambia los valores:

// PATRÓN (de EstadoProducto.java): public enum EstadoProducto { ACTIVO, INACTIVO, DESCONTINUADO } // ADAPTADO a EstadoConsultorio.java: public enum EstadoConsultorio { DISPONIBLE, OCUPADO, MANTENIMIENTO }

Un enum es lo más simple: una línea por valor. Si tu módulo no tiene estados, saltas este paso.

04 Fase 4: DTOs (Request / Response)

Los DTOs son records de Java. Lo que entra (Request) y lo que sale (Response). Copias el patrón y cambias los campos.

4.1
Crear Request
ADAPTAR

Copia de etiquetas/application/dto/EtiquetaRequest.java. Cambia los campos y las validaciones:

// PATRÓN (de EtiquetaRequest.java): public record EtiquetaRequest( @NotBlank(message = "El nombre es obligatorio") @Size(max = 40) String nombre, String color, Boolean activa ) {} // ADAPTADO a ClinicaRequest.java: public record ClinicaRequest( @NotBlank(message = "La razón social es obligatoria") @Size(max = 150) String razonSocial, @NotBlank(message = "El RUC es obligatorio") @Size(min = 11, max = 11, message = "El RUC debe tener 11 dígitos") String ruc, @Size(max = 20) String telefono, Boolean activo ) {}
Las validaciones son lo NUEVO. El patrón del record es siempre igual, pero las anotaciones @NotBlank, @Size, @Pattern dependen de las reglas de tu entidad. Para el examen: RUC de exactamente 11 dígitos y razón social obligatoria. Si no pones @Size(min=11, max=11), el backend no rechaza el RUC corto y pierdes el punto de validación.
4.2
Crear Response
ADAPTAR

Copia de etiquetas/application/dto/EtiquetaResponse.java. El Response tiene los mismos campos que el Request pero incluye el id y puede tener campos calculados:

// ADAPTADO a ClinicaResponse.java: public record ClinicaResponse( Long id, String ruc, String razonSocial, String telefono, Boolean activo ) {}

05 Fase 5: Puertos (interfaces)

Los puertos son interfaces. Port IN = lo que el mundo puede pedir. Port OUT = lo que el núcleo necesita de fuera. Copias el patrón y cambias los nombres de los métodos.

5.1
Port IN (use case)
ADAPTAR

Copia de productos/application/port/in/ManageProductoUseCase.java. Cambia los nombres de los métodos:

// PATRÓN (de ManageProductoUseCase.java): public interface ManageProductoUseCase { List<ProductoResponse> listar(); ProductoResponse obtener(Long id); ProductoResponse crear(ProductoRequest request); ProductoResponse actualizar(Long id, ProductoRequest request); void eliminar(Long id); } // ADAPTADO a ManageClinicaUseCase.java: public interface ManageClinicaUseCase { List<ClinicaResponse> listar(); ClinicaResponse obtener(Long id); ClinicaResponse crear(ClinicaRequest request); ClinicaResponse actualizar(Long id, ClinicaRequest request); void eliminar(Long id); }

Los métodos del CRUD son siempre los mismos 5. Si necesitas filtros o operaciones extra, las agregas aquí.

5.2
Port OUT (persistencia)
ADAPTAR

Copia de etiquetas/application/port/out/EtiquetaPersistencePort.java. Cambia el tipo de retorno y los métodos:

// ADAPTADO a ClinicaPersistencePort.java: public interface ClinicaPersistencePort { List<Clinica> findAll(); Optional<Clinica> findById(Long id); boolean existsByRuc(String ruc); boolean existsByRucAndIdNot(String ruc, Long id); Clinica save(Clinica clinica); void deleteById(Long id); }
El Port OUT devuelve el dominio (Clinica), nunca la entidad JPA (ClinicaEntity). La conversión la hace el adapter.

06 Fase 6: Entidades JPA + Repositories

La entidad JPA es la única clase que conoce la tabla de la base de datos. El repository es la interfaz que hace las consultas. Ambos se copian y adaptan.

6.1
Crear la entidad JPA
ADAPTAR

Copia de etiquetas/adapters/out/persistence/entity/EtiquetaEntity.java. Cambia @Table, @Column y los campos:

// PATRÓN (de EtiquetaEntity.java): @Entity @Table(name = "CRM_ETIQUETAS") @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class EtiquetaEntity { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @Column(name = "ID_ETIQUETA") private Long id; @Column(name = "NOMBRE") private String nombre; } // ADAPTADO a ClinicaEntity.java: @Entity @Table(name = "CLINICAS", schema = "EXA_CLINICA") ← OJO: schema distinto @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class ClinicaEntity { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @Column(name = "ID") private Long id; @Column(name = "RUC", length = 11, nullable = false, unique = true) private String ruc; @Column(name = "RAZON_SOCIAL", nullable = false) private String razonSocial; @Column(name = "TELEFONO") private String telefono; @Column(name = "ACTIVO") private Integer activo = 1; }
Cuidado con schema. Los módulos normales del proyecto usan el esquema BOM_VENTAS (sin especificar schema en la entidad). El módulo clínica usa un esquema separado EXA_CLINICA, por eso la entidad lleva schema = "EXA_CLINICA". Si no lo pones, Hibernate busca en el esquema por defecto y no encuentra la tabla.
6.2
Crear el repository Spring Data
ADAPTAR

Copia de etiquetas/adapters/out/persistence/repository/EtiquetaSpringDataRepository.java. Cambia el tipo de entidad y los métodos de búsqueda:

// PATRÓN (de EtiquetaSpringDataRepository.java): @Repository public interface EtiquetaSpringDataRepository extends JpaRepository<EtiquetaEntity, Long> { boolean existsByNombreNormalizado(String n); } // ADAPTADO a ClinicaRepository.java: @Repository public interface ClinicaRepository extends JpaRepository<ClinicaEntity, Long> { boolean existsByRuc(String ruc); boolean existsByRucAndIdNot(String ruc, Long id); }
Spring Data genera la implementación automáticamente. No escribes ni una línea de SQL. El nombre del método es la consulta: existsByRuc = SELECT 1 FROM ... WHERE ruc = ?. Solo agregas los métodos que necesitas para validar (unique check).

07 Fase 7: Persistence Adapter

El adapter es el puente entre el dominio y la entidad JPA. Implementa el Port OUT usando el repository. Copias el patrón y cambias los mapeos.

7.1
Crear el persistence adapter
ADAPTAR

Copia de etiquetas/adapters/out/persistence/EtiquetaPersistenceAdapter.java. Cambia los mapeos toEntity/toDomain:

// PATRÓN (de EtiquetaPersistenceAdapter.java): @Component @RequiredArgsConstructor public class EtiquetaPersistenceAdapter implements EtiquetaPersistencePort { private final EtiquetaSpringDataRepository repository; public Etiqueta save(Etiqueta etiqueta) { return toDomain(repository.save(toEntity(etiqueta))); } // toEntity y toDomain mapean campo a campo } // ADAPTADO a ClinicaPersistenceAdapter.java: @Component @RequiredArgsConstructor public class ClinicaPersistenceAdapter implements ClinicaPersistencePort { private final ClinicaRepository repository; @Override public Clinica save(Clinica clinica) { return toDomain(repository.save(toEntity(clinica))); } private ClinicaEntity toEntity(Clinica c) { return ClinicaEntity.builder() .id(c.getId()).ruc(c.getRuc()) .razonSocial(c.getRazonSocial()) .telefono(c.getTelefono()) .activo(c.getActivo()) .build(); } private Clinica toDomain(ClinicaEntity e) { return Clinica.builder() .id(e.getId()).ruc(e.getRuc()) .razonSocial(e.getRazonSocial()) .telefono(e.getTelefono()) .activo(e.getActivo()) .build(); } }
Lo que cambia: solo los campos del toEntity y toDomain. Lo que NO cambia: la estructura de la clase, el @Component, el @RequiredArgsConstructor, que implementa el Port OUT, que usa el repository.

08 Fase 8: Service (reglas de negocio)

El service es donde está la lógica de verdad. Aquí es donde piensas. La estructura se copia, pero las reglas se escriben nuevas.

8.1
La estructura (copiar)
COPIAR

La estructura del service es siempre la misma. Copia de etiquetas/application/service/EtiquetaService.java:

@Service @RequiredArgsConstructor @Transactional public class ClinicaService implements ManageClinicaUseCase { private final ClinicaPersistencePort persistencePort; ← inyecta el puerto @Override @Transactional(readOnly = true) public List<ClinicaResponse> listar() { ... } @Override @Transactional(readOnly = true) public ClinicaResponse obtener(Long id) { ... } @Override public ClinicaResponse crear(ClinicaRequest request) { ... } @Override public ClinicaResponse actualizar(Long id, ClinicaRequest request) { ... } @Override public void eliminar(Long id) { ... } }

Lo que NO cambia nunca: @Service, @RequiredArgsConstructor, @Transactional, que implementa el Port IN, que inyecta el Port OUT, los métodos read-only en las lecturas.

8.2
Las reglas de negocio (nuevo)
NUEVO

Aquí es donde piensas. El patrón del CRUD se copia, pero qué validas y cómo es específico de tu módulo:

// NUEVO: validar que el RUC no exista antes de crear public ClinicaResponse crear(ClinicaRequest request) { if (persistencePort.existsByRuc(request.ruc())) { throw new IllegalArgumentException( "Ya existe una clínica con el RUC: " + request.ruc()); } Clinica clinica = Clinica.builder() .ruc(request.ruc()) .razonSocial(request.razonSocial()) .telefono(request.telefono()) .activo(request.activo() == null || request.activo() ? 1 : 0) .build(); return toResponse(persistencePort.save(clinica)); } // NUEVO: validar RUC único al actualizar (excluyendo el propio ID) public ClinicaResponse actualizar(Long id, ClinicaRequest request) { Clinica clinica = findOrThrow(id); if (persistencePort.existsByRucAndIdNot(request.ruc(), id)) { throw new IllegalArgumentException("RUC ya existe"); } clinica.setRuc(request.ruc()); clinica.setRazonSocial(request.razonSocial()); // ... actualizar campos return toResponse(persistencePort.save(clinica)); }
Qué es NUEVO en el service:
  • Las validaciones de unicidad: ¿el RUC ya existe? ¿el código de consultorio ya existe?
  • Las reglas de campo: ¿ACTIVO es 0 o 1? ¿la tarifa es > 0?
  • El toResponse: convierte dominio a DTO. Cada módulo tiene los suyos.
  • La excepción: usa ResourceNotFoundException de shared.exception para el 404, IllegalArgumentException para el 400.

09 Fase 9: Controller (REST)

El controller es lo más mecánico de todo. Recibe HTTP, delega al use case y responde. Cero lógica de negocio.

9.1
Crear el controller
ADAPTAR

Copia de etiquetas/adapters/in/web/EtiquetaController.java. Cambia el path, el use case y los DTOs:

// PATRÓN (de EtiquetaController.java): @RestController @RequestMapping("/api/v1/etiquetas") @RequiredArgsConstructor public class EtiquetaController { private final ManageEtiquetaUseCase useCase; @GetMapping public ResponseEntity<List<EtiquetaResponse>> listar() { return ResponseEntity.ok(useCase.listar()); } @PostMapping public EtiquetaResponse crear(@Valid @RequestBody EtiquetaRequest request) { return useCase.crear(request); } // ... resto igual } // ADAPTADO a ClinicaController.java: @RestController @RequestMapping("/api/clinica/clinicas") ← cambia el path @RequiredArgsConstructor public class ClinicaController { private final ManageClinicaUseCase useCase; ← cambia el use case @GetMapping public ResponseEntity<List<ClinicaResponse>> listar() { ← cambia el DTO return ResponseEntity.ok(useCase.listar()); } @PostMapping public ResponseEntity<ClinicaResponse> crear( @Valid @RequestBody ClinicaRequest request) { return ResponseEntity.status(HttpStatus.CREATED) .body(useCase.crear(request)); } // ... resto igual, cambiando tipos }
El controller es el archivo más fácil de adaptar. Cambias 3 cosas: el @RequestMapping, el tipo del useCase, y los tipos de los DTOs en las firmas. La estructura (los @GetMapping, @PostMapping, @PathVariable, @RequestBody) es siempre igual.

10 Fase 10: Frontend — model + service

El frontend de Angular sigue el mismo patrón: un modelo (interfaces), un service (llamadas HTTP) y componentes (pantallas).

10.1
Crear el model
ADAPTAR

Copia de productos/producto.model.ts. Cambia los campos:

// ADAPTADO a clinica.model.ts: export interface Clinica { id?: number; ruc: string; razonSocial: string; telefono?: string; activo?: boolean; } export type EstadoConsultorio = 'DISPONIBLE' | 'OCUPADO' | 'MANTENIMIENTO'; export interface Especialidad { id: number; codigo: string; nombre: string; } export interface ConsultorioRequest { idClinica: number; codigo: string; tarifaHora: number; estado: EstadoConsultorio; especialidadIds: number[]; ← N:M: lista de IDs } export interface ConsultorioResponse { id: number; idClinica: number; clinicaRazonSocial: string; codigo: string; tarifaHora: number; estado: EstadoConsultorio; especialidades: Especialidad[]; ← N:M: lista completa }
Lo NUEVO del N:M en el model: ConsultorioRequest lleva especialidadIds: number[] (los IDs que el usuario eligió) y ConsultorioResponse lleva especialidades: Especialidad[] (los objetos completos para mostrar en el detalle). Esto no aparece en un CRUD simple.
10.2
Crear el service
ADAPTAR

Copia de productos/productos.service.ts. Cambia los paths:

@Injectable({ providedIn: 'root' }) export class ClinicaService { constructor(private http: HttpClient, private apiService: ApiService) {} listarClinicas(): Observable<Clinica[]> { return this.http.get<Clinica[]>( this.apiService.buildUrl('/clinica/clinicas')); ← cambia el path } crearClinica(clinica: Clinica): Observable<Clinica> { return this.http.post<Clinica>( this.apiService.buildUrl('/clinica/clinicas'), clinica); } // ... resto de métodos (obtener, actualizar, eliminar) }
El service es copiar y cambiar el path. La estructura (HttpClient, Observable, buildUrl) es siempre la misma. Solo cambias la URL y el tipo de retorno.

Listado
ADAPTAR

Copia de productos/producto-list/producto-list.ts. Cambia las columnas de la tabla y los botones de acción:

  • El TS: mismo patrón: signals, ngOnInit, cargar(), eliminar()
  • El HTML: cambia las columnas de la tabla: RUC, Razón social, Teléfono, Activa

11.2
Formulario
ADAPTAR

Copia de productos/producto-form/producto-form.ts. Cambia los campos del FormGroup y las validaciones:

// ADAPTADO a clinica-form.ts: this.form = this.fb.group({ ruc: ['', [Validators.required, Validators.minLength(11), Validators.maxLength(11)]], razonSocial: ['', [Validators.required]], telefono: [''], activo: [true] }); // En el HTML, mostrar errores con *ngIf: // <div *ngIf="form.get('ruc').invalid && form.get('ruc').touched"> // El RUC debe tener 11 dígitos // </div>
Las validaciones del frontend son NUEVAS. El patrón del FormGroup se copia, pero Validators.minLength(11) y Validators.required dependen de tu entidad. 12 Fase 12: El caso N:M (consultorios)

Hasta aquí todo era copiar y adaptar el patrón CRUD. El consultorio con especialidades es la parte que no existe en ningún módulo simple: una cabecera (consultorio) con detalles (especialidades) en una relación muchos-a-muchos.

Esta fase es lo que separa un CRUD simple de un módulo completo. Todo lo anterior (fases 1-11) lo haces igual para clínicas que para etiquetas. Esta fase solo aplica cuando tienes una relación N:M con una tabla intermedia.

Qué es NUEVO en cada capa

CapaQué cambia vs un CRUD simpleAcción
SQLTabla intermedia con PK compuesta (dos FKs)NUEVO
Entidad JPA@ManyToMany + @JoinTable en ConsultorioEntityNUEVO
Request DTOLleva especialidadIds: List<Long> además de los campos normalesNUEVO
Response DTOLleva especialidades: List<EspecialidadResponse> (objetos completos)NUEVO
ServiceAl crear: busca las especialidades por ID y las asigna al Set antes de guardarNUEVO
Frontend formTabla dinámica: dropdown de especialidades + botón agregar + botón quitarNUEVO
Frontend detailTabla de solo lectura con las especialidades asignadasADAPTAR
12.1
Entidad con @ManyToMany
NUEVO

La entidad ConsultorioEntity tiene algo que ninguna entidad simple tiene: un Set de especialidades mapeado con @ManyToMany:

@Entity @Table(name = "CONSULTORIOS", schema = "EXA_CLINICA") @Getter @Setter @NoArgsConstructor @AllArgsConstructor @Builder public class ConsultorioEntity { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @ManyToOne(fetch = FetchType.EAGER) @JoinColumn(name = "ID_CLINICA") private ClinicaEntity clinica; ← FK a clínica @Column(name = "CODIGO") private String codigo; @Column(name = "TARIFA_HORA") private BigDecimal tarifaHora; @Enumerated(EnumType.STRING) @Column(name = "ESTADO") private EstadoConsultorio estado; // ← ESTO ES LO NUEVO: @ManyToMany(fetch = FetchType.EAGER) @JoinTable( name = "CONSULTORIO_ESPECIALIDAD", schema = "EXA_CLINICA", joinColumns = @JoinColumn(name = "ID_CONSULTORIO"), inverseJoinColumns = @JoinColumn(name = "ID_ESPECIALIDAD") ) @Builder.Default private Set<EspecialidadEntity> especialidades = new HashSet<>(); }
Qué hace JPA por ti: cuando guardas un ConsultorioEntity que tiene 2 especialidades en su Set, JPA inserta la fila en CONSULTORIOS y automáticamente inserta 2 filas en CONSULTORIO_ESPECIALIDAD. No tienes que escribir SQL para la tabla intermedia. Si borras el consultorio, JPA borra las filas intermedias automáticamente.
12.2
Service que maneja la N:M
NUEVO

El service de consultorio hace algo que el de clínicas no hace: buscar las especialidades por ID y asignarlas:

public ConsultorioResponse crearConsultorio(ConsultorioRequest request) { // 1. Validar que la clínica existe ClinicaEntity clinica = clinicaRepository.findById(request.idClinica()) .orElseThrow(() -> new ResourceNotFoundException("Clínica no encontrada")); // 2. Validar que el código no exista if (consultorioRepository.existsByCodigo(request.codigo())) { throw new IllegalArgumentException("Código ya existe"); } // 3. NUEVO: buscar las especialidades por los IDs que mandó el frontend Set<EspecialidadEntity> especialidades = new HashSet<>(); if (request.especialidadIds() != null && !request.especialidadIds().isEmpty()) { especialidades.addAll(especialidadRepository.findAllById(request.especialidadIds())); } // 4. Construir el consultorio CON las especialidades ConsultorioEntity entity = ConsultorioEntity.builder() .clinica(clinica) .codigo(request.codigo()) .tarifaHora(request.tarifaHora()) .estado(request.estado()) .especialidades(especialidades) ← N:M: se asignan aquí .build(); // 5. Guardar — JPA inserta en CONSULTORIOS + CONSULTORIO_ESPECIALIDAD return toResponse(consultorioRepository.save(entity)); }
Lo único nuevo vs el service de clínicas son las líneas 3 y 4: buscar las especialidades por ID y pasarlas al builder. El resto (validar clínica, validar código único, guardar) es el mismo patrón.
12.3
Frontend: tabla dinámica de especialidades
NUEVO

El formulario de consultorio tiene algo que el de clínicas no tiene: una tabla donde el usuario agrega y quita especialidades antes de guardar:

// En consultorio-form.ts: // Catálogo de especialidades (cargadas del backend) especialidadesCatalogo: Especialidad[] = []; especialidadSeleccionadaId: number | null = null; // Tabla en memoria: las especialidades que el usuario agregó especialidadesAsignadas: Especialidad[] = []; // NUEVO: agregar especialidad a la tabla agregarEspecialidad() { const esp = this.especialidadesCatalogo .find(e => e.id === Number(this.especialidadSeleccionadaId)); if (esp && !this.especialidadesAsignadas.some(e => e.id === esp.id)) { this.especialidadesAsignadas.push(esp); } } // NUEVO: quitar especialidad de la tabla quitarEspecialidad(id: number) { this.especialidadesAsignadas = this.especialidadesAsignadas .filter(e => e.id !== id); } // Al guardar: mandar los IDs de las especialidades asignadas guardar() { const payload = { ...this.form.value, especialidadIds: this.especialidadesAsignadas.map(e => e.id) }; this.clinicaService.crearConsultorio(payload).subscribe(...); }
Esto es lo más NUEVO de todo el módulo. No existe en producto-form ni en etiqueta-form. El único lugar del proyecto que hace algo parecido es actividad-form (que tiene un selector de etiquetas), pero la lógica es distinta. Aquí debes pensar: cómo llenar el dropdown, cómo agregar a la tabla, cómo evitar duplicados, cómo quitar.
