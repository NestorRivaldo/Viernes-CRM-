P1 ¿Por qué `Actividad` y `ActividadEntity` son clases distintas si tienen los mismos atributos?
▼

Respuesta arquitectónica: Por el principio de Inversión de Dependencias y Aislamiento de Dominio de la Arquitectura Hexagonal.

El dominio (Actividad.java) no debe tener dependencias hacia tecnologías externas de infraestructura como Hibernate o Jakarta Persistence. Si en el futuro se migra el motor a MongoDB, JDBC plano o microservicios, el dominio no cambia en absoluto; únicamente se implementa un nuevo ActividadPersistencePort.

📌 Archivo ancla: ActividadPersistenceAdapter.java:82-106 es el encargado de hacer la traducción bidireccional (toEntity y toDomain).
P2 ¿Cómo se garantiza la integridad si en la base de datos no hay una FK física entre `CRM_ACTIVIDADES` y `CRM_CLIENTES`?
▼

Respuesta arquitectónica: La integridad referencial entre módulos es lógica y está garantizada por la capa de aplicación antes de persistir. 

// ActividadService.java:235-248
private void validarRelaciones(ActividadRequest request) {
    if (request.idCliente() != null && !validationPort.existeCliente(request.idCliente())) {
        throw new ResourceNotFoundException("Cliente no encontrado con ID: " + request.idCliente());
    }
    if (request.idLead() != null && !validationPort.existeLead(request.idLead())) {
        throw new ResourceNotFoundException("Lead no encontrado con ID: " + request.idLead());
    }
    if (request.idUsuario() != null && !validationPort.existeUsuario(request.idUsuario())) {
        throw new ResourceNotFoundException("Usuario no encontrado con ID: " + request.idUsuario());
    }
}

Esto desacopla el ciclo de vida de los módulos a nivel de esquema de base de datos en Oracle, permitiendo que cada módulo gobierne su propio ciclo sin bloqueos en cascada.

P3 ¿Cómo gestiona `ActividadService` las transacciones y las optimizaciones de lectura?
▼

Respuesta arquitectónica: Mediante Spring Declarative Transaction Management con distinción de transacciones de lectura vs escritura.

  • A nivel de clase ([línea 36](file:///e:/Viernes/Viernes/viernes-backend/src/main/java/com/viernes/actividades/application/service/ActividadService.java#L36)), se anota con @Transactional. Esto hace que métodos como crear(), actualizar() y eliminar() se ejecuten dentro de una transacción con capacidad de escritura.
  • Los métodos de consulta como listarTodos() y obtener(id) sobreescriben la configuración con @Transactional(readOnly = true).
⚡ Beneficio de rendimiento: readOnly = true desactiva la detección sucia (dirty checking) de entidades en el Session/EntityManager de Hibernate, consumiendo menos CPU y liberando la conexión de HikariCP más rápido.
P4 ¿Por qué las pruebas unitarias de `ActividadService` corren en milisegundos sin levantar Oracle?
▼

Respuesta arquitectónica: Gracias a los Puertos de Salida (Ports Out), el servicio se prueba con mocks puros de Mockito (@ExtendWith(MockitoExtension.class)). 

// ActividadServiceTest.java:38-57
@Mock private ActividadPersistencePort persistencePort;
@Mock private RelacionValidationPort validationPort;
@Mock private ActividadParticipantePersistencePort participantePort;
@InjectMocks private ActividadService servicio;

No se levanta el contexto de Spring (@SpringBootTest) ni Docker. Se mockean únicamente las interfaces de persistencia y validación, permitiendo probar toda la lógica de negocio en menos de 50 milisegundos.

P5 ¿Qué es la Brecha B9 de arquitectura y cómo afecta a `ContactoQueryAdapter`?
▼

Respuesta arquitectónica: Es un residuo de diseño donde se realiza una consulta ineficiente en memoria debido a la falta de un método específico en el módulo proveedor. 

// ContactoQueryAdapter.java:31-34
return clienteUseCase.listar().stream()
        .flatMap(cliente -> cliente.contactos().stream())
        .filter(contacto -> contacto.id().equals(idContacto))
        .findFirst();

Para buscar un solo contacto por ID, se invoca clienteUseCase.listar() que trae todos los clientes con todos sus contactos a memoria y los filtra con Java Streams.

🛠️ Solución: Exponer buscarContactoPorId(Long id) directamente en el puerto público ManageClienteUseCase para que la consulta la resuelva Oracle con un WHERE ID = :id indexado.
