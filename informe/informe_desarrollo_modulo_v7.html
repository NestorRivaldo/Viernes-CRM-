01 Qué es un módulo

Un módulo es una capacidad de negocio completa (clientes, actividades, oportunidades, etiquetas…) empaquetada con el mismo esqueleto de arquitectura hexagonal. No es una carpeta arbitraria: Spring Modulith la reconoce por su package-info.java.

La idea central es simple: cada módulo encapsula todo lo relacionado con una capacidad de negocio — su lógica, sus datos, su API — y se comunica con los demás a través de interfaces bien definidas (puertos). Cambias un módulo sin romper los demás.

Encapsulamiento
Cada módulo se aisla

Su lógica de negocio no se filtra a otros módulos. El contacto entre módulos es por interfaces (puertos), nunca por acceso directo a repositorios ajenos.

Mismo esqueleto
Todos se navegan igual

Las carpetas se repiten: domain, application, adapters. Aprende uno, sabes navegar todos.

Independencia tecnológica
El núcleo no sabe de BD

El dominio y los casos de uso no conocen JPA, Oracle ni HTTP. Solo los adapters tocan tecnología.

Regla de dependencia: adapters → application → domain. El núcleo nunca importa a los adapters. Spring inyecta las implementaciones en runtime.

02 Las tres capas del hexágono

Cada módulo tiene tres capas con una dirección de dependencia estricta: de afuera hacia adentro, nunca al revés.

adapter in (entra HTTP) adapter out persistence (sale a Oracle) adapter out external (sale a APIs) puertos (costuras) domain (núcleo puro)

04 package-info.java — el carnet del módulo

Cada módulo tiene un package-info.java que lo registra ante Spring Modulith. Define su tipo (OPEN o CLOSED por defecto) y a qué módulos puede depender.

Módulo OPEN (permite que otros módulos accedan a sus internals)

@org.springframework.modulith.ApplicationModule( type = org.springframework.modulith.ApplicationModule.Type.OPEN, allowedDependencies = {"clientes", "oportunidades", "leads", "etiquetas", "usuarios", "shared"} ) package com.viernes.actividades; // actividades necesita leer datos de clientes, leads, oportunidades, etiquetas y usuarios

Módulo CLOSED (solo expone su API pública, sin allowedDependencies)

@org.springframework.modulith.ApplicationModule( allowedDependencies = {"shared", "shared.exception"} ) package com.viernes.usuarios; // usuarios es CLOSED por defecto: otros módulos solo pueden usar UsuariosApi, no sus repos
OPEN vs CLOSED: OPEN deja que otros módulos accedan a tus clases internas (repositorios, adapters). CLOSED obliga a consumir solo la API pública (puertos port/in). Usa CLOSED por defecto; abre solo cuando hay cruce de datos legítimo.

05 El dominio (domain)

El dominio es el núcleo puro del módulo: clases POJO y enums que representan el negocio. No dependen de JPA, Spring ni ninguna tecnología. Si quitas Spring, el dominio compila igual.

package com.viernes.actividades.domain; import java.time.LocalDateTime; public class Actividad { private Long id; private String idUsuario; private Long idCliente; private TipoActividad tipo; private String titulo; private EstadoActividad estado; private LocalDateTime fecha; private LocalDateTime creadoEn; // ... getters y setters }
POJO
Clase simple

Campos privados + getters/setters. Constructor vacío y con todos los parámetros. Sin anotaciones de framework.

Enums
Estados y tipos

EstadoActividad (PENDIENTE, EN_PROGRESO, COMPLETADA, CANCELADA). TipoActividad (LLAMADA, EMAIL, REUNION...).

Sin dependencias
Puro Java

No importa JPA, Spring, ni nada. Solo java.time y java.util.

06 Los puertos (port in / port out)

Los puertos son interfaces en application. Son la costura que permite cambiar la tecnología sin tocar el núcleo.

Port IN — lo que el mundo puede pedirle al módulo

package com.viernes.actividades.application.port.in; public interface ManageActividadUseCase { ActividadResponse crear(ActividadRequest request); ActividadResponse obtener(Long id); List<ActividadResponse> listarTodos(); ActividadResponse cambiarEstado(Long id, EstadoActividad estado); // ... 15 métodos en total }

Port OUT — lo que el núcleo necesita de fuera

package com.viernes.actividades.application.port.out; public interface ActividadPersistencePort { Actividad save(Actividad actividad); Optional<Actividad> findById(Long id); List<Actividad> findAll(); void deleteById(Long id); } public interface ContactoQueryPort { Optional<ContactoInfo> buscarPorId(Long contactoId); }
PuertoQuién lo DEFINEQuién lo IMPLEMENTAQuién lo LLAMA
port/inapplicationapplication/serviceadapters/in/web (controller)
port/outapplicationadapters/out (persistence, external)application/service
Inversión de dependencia: el núcleo define la interfaz port/out y el adapter de tecnología la implementa. Por eso application no importa Oracle ni APIsPERU. El service puede testearse con mocks de los puertos, sin BD ni red.

07 El servicio (service)

El service es el corazón del módulo: implementa port/in, orquesta port/out y aplica las reglas de negocio. Lleva @Transactional.

@Service @Transactional public class ActividadService implements ManageActividadUseCase { private final ActividadPersistencePort persistencePort; private final RelacionValidationPort validationPort; private final ActividadEtiquetaPersistencePort etiquetaPort; public ActividadService(ActividadPersistencePort persistencePort, ...) { this.persistencePort = persistencePort; // ... inyección por constructor (sin @Autowired) } @Override public ActividadResponse crear(ActividadRequest request) { validarRelaciones(request); // usa port/out etiquetaIdsValidos(request); // regla: máx 8 etiquetas Actividad actividad = new Actividad(...); // construye dominio persistencePort.save(actividad); // usa port/out sincronizarEtiquetas(actividad, request.etiquetaIds()); return toResponse(actividad); // convierte a DTO } }
El service NO debe: conocer HTTP (sin HttpServletRequest), conocer JPA (sin EntityManager), ni devolver entidades JPA. Trabaja con el dominio y devuelve DTOs.

08 Los DTOs (Data Transfer Objects)

Los DTOs son los contratos de entrada y salida. Lo que viaja por HTTP. Se definen como records en application/dto/.

public record ActividadRequest( String titulo, String tipo, Long idCliente, Long idLead, Long idOportunidad, String idUsuario, List<Long> etiquetaIds ) {} public record ActividadResponse( Long id, String titulo, String tipo, String estado, LocalDateTime fecha, boolean esVencida, List<ParticipanteResponse> participantes, List<EtiquetaResponse> etiquetas ) {}
Request
Entrada

Lo que el cliente envía. Campos con validación @NotBlank, @NotNull si se anota con Jakarta Validation.

Response
Salida

Lo que el módulo devuelve. Puede incluir campos calculados (esVencida) que no existen en la entidad.

Records
Inmutables

Se usan Java records: compactos, inmutables, con getters automáticos. No llevan lógica.

09 El controller (adapter in/web)

El controller es el único punto de entrada HTTP del módulo. Recibe la petición, la delega al caso de uso y arma la respuesta. Cero lógica de negocio.

@RestController @RequestMapping("/api/v1/actividades") public class ActividadController { private final ManageActividadUseCase useCase; public ActividadController(ManageActividadUseCase useCase) { this.useCase = useCase; } @PostMapping public ResponseEntity<ActividadResponse> crear(@Valid @RequestBody ActividadRequest request) { ActividadResponse response = useCase.crear(request); return new ResponseEntity<>(response, HttpStatus.CREATED); } @GetMapping("/{id}") public ResponseEntity<ActividadResponse> obtener(@PathVariable Long id) { return ResponseEntity.ok(useCase.obtener(id)); } }
El controller depende de la interfaz ManageActividadUseCase, no de ActividadService. Spring inyecta la implementación en runtime. Esto es la inversión de dependencia en acción.

10 El persistence adapter (adapter out)

El adapter de salida implementa port/out usando JPA. Es la única capa que toca Oracle. Convierte entre el dominio y la entidad JPA.

La entidad JPA

@Entity @Table(name = "CRM_ACTIVIDADES") public class ActividadEntity { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(name = "TITULO", nullable = false) private String titulo; @Column(name = "ESTADO", nullable = false) private String estado; @Column(name = "FECHA", nullable = false) private LocalDateTime fecha; // ... resto de campos }

El repository Spring Data

public interface ActividadSpringDataRepository extends JpaRepository<ActividadEntity, Long> { List<ActividadEntity> findByEstado(String estado); List<ActividadEntity> findByIdCliente(Long idCliente); }

El adapter que une todo

@Component public class ActividadPersistenceAdapter implements ActividadPersistencePort { private final ActividadSpringDataRepository repository; @Override public Actividad save(Actividad actividad) { ActividadEntity entity = toEntity(actividad); ActividadEntity saved = repository.save(entity); return toDomain(saved); } @Override public Optional<Actividad> findById(Long id) { return repository.findById(id).map(this::toDomain); } }
Mapeo manual: la conversión entre dominio y entidad se hace a mano (métodos toEntity / toDomain). MapStruct está declarado en el pom.xml pero sin uso real. La carpeta mapper/ que existe en algunos módulos está vacía.

11 La base de datos (Oracle)

Cada módulo tiene su(s) tabla(s) en Oracle, definidas en base de datos/03_tablas/. El esquema es BOM_VENTAS y las tablas siguen el prefijo CRM_.

12 Comunicación entre módulos

Un módulo no llama a otro directamente: usa puertos out cuyos adapters consumen la API pública del otro módulo (o sus internals si es OPEN).

El módulo actividades declara en su package-info.java que depende de clientes, oportunidades, leads, etiquetas y usuarios. El acceso a los OPEN es directo a sus repositorios; el acceso a usuarios (CLOSED) es solo por su API pública.

Regla Modulith: nunca importes com.viernes.clientes.adapters.out.persistence.repository desde otro módulo si clientes es CLOSED. Usa su port/in (API pública) en su lugar.

13 Flujo completo de una petición

Así viaja una petición POST /api/v1/actividades de extremo a extremo. Cada salto es una capa distinta.

HTTP llega al controller
POST /api/v1/actividades con un JSON. El controller recibe @Valid @RequestBody ActividadRequest. No valida reglas de negocio; solo delega.
Controller llama al puerto in
El controller conoce ManageActividadUseCase (interfaz), no el service concreto. Spring inyecta ActividadService en runtime.
Service aplica reglas de negocio
ActividadService.crear() valida relaciones (cliente/lead existe), valida máximo 8 etiquetas, construye el dominio y llama persistencePort.save(). Todo en una transacción @Transactional.
Adapter out persiste en Oracle
ActividadPersistenceAdapter.save() convierte dominio → entidad JPA, llama repository.save() → Hibernate ejecuta el INSERT en CRM_ACTIVIDADES.
Service arma la respuesta
toResponse() convierte dominio → ActividadResponse (DTO), calcula campos derivados como esVencida.
Controller devuelve HTTP 201
new ResponseEntity<>(response, HttpStatus.CREATED). El JSON vuelve al cliente. Si algo falló, GlobalExceptionHandler traduce la excepción a 400/404.

15 Errores comunes

Lo que rompe la arquitectura si no se respeta.

ErrorPor qué pasaCómo se corrige
ERROR El service importa EntityManager o JpaRepository El desarrollador salta la capa de adapters y accede a JPA directamente desde el núcleo. Crear un port/out y un adapter que lo implemente. El service solo conoce la interfaz.
ERROR El controller tiene lógica de negocio Se valida una regla (ej: máximo 8 etiquetas) dentro del controller en vez del service. Mover toda regla al service. El controller solo recibe, delega y responde.
ERROR Un módulo importa el repositorio de otro CLOSED Se accede a com.viernes.usuarios.adapters.out.persistence.repository desde otro módulo. Usar la API pública del módulo (port/in) o pedir que lo abran como OPEN si es legítimo.
ERROR Falta package-info.java Spring Modulith no reconoce el módulo y no valida dependencias. Crear el archivo con @ApplicationModule y allowedDependencies.
ERROR El service devuelve la entidad JPA Se devuelve ActividadEntity en vez de ActividadResponse, filtrando la tecnología al exterior. Siempre convertir a DTO con toResponse() antes de devolver.
ERROR El dominio tiene anotaciones JPA Se mezcla @Entity en la clase del dominio, acoplando el núcleo a Hibernate. El dominio es puro. La entidad JPA vive en adapters/out/persistence/entity/ como clase separada.
ERROR Inyección con @Autowired en campo Se usa @Autowired en un campo privado en vez de constructor. Usar inyección por constructor (campo final + constructor). Spring lo hace automático si hay un único constructor.
