01

Resumen ejecutivo

Viernes CRM V1 es un monorepo full-stack con un backend único Spring Boot organizado por módulos de negocio y un frontend Angular con rutas lazy-loaded. El backend aplica Spring Modulith para delimitar módulos y arquitectura hexagonal dentro de cada módulo. La persistencia principal está en Oracle 23c; la identidad se externaliza en Keycloak 25 con PostgreSQL.

04

Arquitectura del backend

El backend es un único proceso Spring Boot, pero internamente está dividido por módulos. Cada módulo funcional replica cuatro zonas: entrada web, aplicación, dominio y persistencia. Spring Modulith comprueba que las dependencias declaradas se respeten.

Flujo de una petición backend

01

Controller

Recibe HTTP, valida DTOs y traduce a caso de uso.

02

Use Case

Puerto de entrada del módulo; desacopla la web de la aplicación.

03

Service

Reglas de negocio, transacciones y validaciones cruzadas.

04

Out Port

Contrato de persistencia o de consulta a otro módulo.

05

Adapter

JPA, entidades y repositorios Spring Data hacia Oracle.

Estructura interna de un módulo

com.viernes.<modulo>/ ├── adapters/ │ ├── in/web/ Controlador REST y mapeo HTTP │ └── out/persistence/ Adaptador, entidad y repositorio JPA ├── application/ │ ├── dto/ Requests y responses (records) │ ├── port/in/ Casos de uso expuestos │ ├── port/out/ Puertos de persistencia o consulta │ └── service/ Implementación de casos de uso ├── domain/ Modelo y enums del negocio └── package-info.java Límites y dependencias del módulo

Lectura de los límites: los módulos OPEN y la ausencia de package-info en actividades hacen que la verificación de Modulith sea más permisiva de lo que sugiere la arquitectura objetivo. Esto no rompe el sistema, pero sí permite acoplamientos que deberían revisarse.

Convenciones y piezas transversales

DTOs

Requests y responses son record en la mayoría de módulos; las validaciones usan Jakarta Validation.

Transacciones

Los servicios usan @Transactional para escritura y readOnly = true para consultas.

Errores

GlobalExceptionHandler centraliza 404, 400, 401, 403, 409 y errores de validación.

Correlación

X-Trace-ID se genera en Angular y se propaga al backend mediante un filtro compartido.

Documentación

Springdoc 3.0.2 expone Swagger UI y anotaciones @Tag/@Operation.

Auditoría técnica

ModularityTests verifica la estructura y genera documentación de módulos.

Reglas de negocio destacadas

Oportunidades y pipeline

Etapas: PROSPECCION → CONTACTO → CALIFICACION → PROPUESTA → NEGOCIACION → GANADA / PERDIDA. El valor ponderado se calcula como valor × probabilidad / 100, con redondeo HALF_UP a dos decimales.

Propuestas

Nacen en BORRADOR; solo se editan o eliminan en ese estado. Pasan a ENVIADA, luego a APROBADA o RECHAZADA; pueden cancelarse si no están en estado terminal. El número es PROP-AAAA-####.

Actividades

Tipos LLAMADA, REUNION, TAREA y SEGUIMIENTO; estados PENDIENTE, EN_PROCESO, COMPLETADA y CANCELADA. Una actividad se considera vencida si sigue pendiente después de su fecha.

Leads y marketing

Estados de lead: NUEVO, CONTACTADO, CALIFICADO, CONVERTIDO y DESCARTADO. Campañas: BORRADOR, ACTIVA, FINALIZADA y CANCELADA.

Clientes y contactos

Cliente con estado ACTIVO/INACTIVO; el contacto pertenece a un cliente y se gestiona como subrecurso. La desactivación es lógica, no borrado físico.

Equipos

Estado ACTIVO/INACTIVO, nombre único y miembros asociados a usuarios. La membresía se agrega y elimina mediante subrecurso.

Mensajería

Sala única para todos los usuarios autenticados. Historial persistente en Oracle, polling cada 5 s y contador de no leídos por navegador. Ver informe específico.

Dashboard

Seis consultas de solo lectura: resumen, KPIs, pipeline, leads, actividades y propuestas. No tiene tabla propia; consume el estado actual de los demás módulos.

Núcleo del frontend

core/auth

AuthService gestiona login, token, usuario y roles. authGuard protege el layout; roleGuard restringe usuarios a ADMIN. Existe un adaptador Keycloak adicional, pero el proveedor registrado en app.config.ts es el servicio principal.

core/interceptors

traceIdInterceptor agrega X-Trace-ID; jwtInterceptor agrega el Bearer, aplica timeout de 15 s y maneja 401 (logout) y 403 (aviso).

core/layout

Shell con sidebar, cabecera, menú de usuario, notificaciones estáticas y botón de mensajes con badge. Renderiza el router-outlet y el panel de chat.

core/services

ApiService centraliza la URL base desde environment.ts. Los servicios de feature construyen sus rutas relativas.

Seguridad e identidad

La seguridad se apoya en Keycloak como proveedor OIDC y en Spring Security como resource server. El frontend obtiene un access token, lo guarda y lo adjunta a cada llamada al backend. Los roles viajan en realm_access.roles y se convierten en autoridades ROLE_*.

ElementoConfiguración actual
Realmviernes-realm en http://localhost:8180.
Cliente frontendviernes-frontend, público, Standard Flow y Direct Grant habilitados; redirects a localhost:4200.
Cliente backendviernes-backend, bearer-only.
Usuario demoadmin@viernes.com con roles ADMIN, JEFE y VENDEDOR.
Issuer / JWKhttp://localhost:8180/realms/viernes-realm y endpoint /protocol/openid-connect/certs.
Backend público/api/v1/auth/**, Swagger, actuator y recursos estáticos.

Flujo de autenticación actual

1
Login
El usuario ingresa correo y contraseña. El formulario está precargado con las credenciales demo.
2
AuthService
Envía grant_type=password al endpoint /protocol/openid-connect/token del cliente público.
3
Keycloak
Valida credenciales y devuelve access_token y refresh_token.
4
Navegador
Guarda tokens y usuario en localStorage; decodifica claims para nombre, correo y roles.
5
Interceptor
Adjunta Authorization: Bearer … a las llamadas al backend; no lo hace en llamadas a Keycloak ni en /auth/.
6
Resource Server
Valida firma, emisor y expiración; convierte roles y establece el principal con preferred_username.

Fortalezas

  • Identidad centralizada y estándar OIDC.
  • Roles de realm mapeados a autoridades Spring.
  • API stateless, sin sesión de servidor.
  • Guard de rol para la administración de usuarios.
  • Timeout de 15 s y mensajes de error amigables.

Brechas

  • Access token en localStorage; expuesto ante XSS.
  • No hay refresh automático efectivo en AuthService; al expirar se fuerza logout.
  • Direct Grant es un flujo heredado, no el recomendado para SPA.
  • El login local del backend no es aceptado por el resource server en perfil Keycloak.
  • Actuator y Swagger están abiertos sin autenticación.
  • Credenciales demo y secretos en archivos del repositorio.
Dualidad de autenticación: conviven un login JWT local (/api/v1/auth/login) y el login Keycloak. En el perfil activo keycloak, el backend valida tokens de Keycloak; el token local no sirve para autenticarse. Antes de producción debe elegirse un único camino y retirar el otro o aislarlo por perfil.

Decisiones de modelado

  • Agregados por ID: los módulos no dependen de entidades JPA ajenas.
  • Snapshots: la propuesta guarda descripción y precio del producto al momento de cotizar.
  • Integridad en aplicación: los adaptadores validan existencia de referencias antes de guardar.
  • Desactivación lógica: usuarios, clientes, productos y equipos manejan estado en lugar de borrado indiscriminado.

Cuidados

  • No hay migraciones versionadas; el esquema depende de ddl-auto=update.
  • Las referencias lógicas no tienen FK física: la integridad depende del código.
  • Los borrados en cascada se resuelven manualmente en algunos servicios.
  • No hay campos de auditoría uniformes (creado_por, actualizado_en) en todas las tablas.

Flujos de negocio actuales

El sistema cubre el ciclo comercial desde el lead hasta la propuesta, con actividades de seguimiento y un dashboard agregado. Estos son los recorridos principales tal como están implementados.

FlujoPasosReglas / efecto
Autenticación Login → Keycloak → token → localStorage → interceptor → backend. El backend valida el JWT; el frontend guarda usuario y roles. Al expirar, logout y redirección.
Cliente y contacto Crear cliente → agregar contactos → consultar/editar → desactivar. El contacto pertenece al cliente; la desactivación evita borrar historial.
Lead Registrar lead → asignar fuente → cambiar estado → convertir/descartar. Estados NUEVO → CONTACTADO → CALIFICADO → CONVERTIDO / DESCARTADO.
Oportunidad Crear oportunidad → asociar contactos, productos y colaboradores → avanzar etapa. El valor ponderado se recalcula en la respuesta; las asociaciones evitan duplicados.
Propuesta Seleccionar oportunidad y cliente → agregar detalles → calcular totales → enviar → aprobar/rechazar/cancelar. Solo BORRADOR es editable; las transiciones son explícitas; el detalle conserva snapshot del producto.
Actividad Crear actividad → vincular cliente/lead/oportunidad → agregar participantes → cambiar estado. Puede estar vencida si sigue pendiente después de la fecha; los participantes son contactos.
Campaña Crear campaña → activar → asociar leads → finalizar/cancelar. Backend operativo; la SPA no expone pantalla y redirige /campanas a dashboard.
Dashboard Consultar resumen, KPIs, pipeline, leads, actividades y propuestas. Consultas de solo lectura sobre el estado actual; no almacena agregados.
Mensajería Abrir panel → cargar últimos 100 → enviar → polling incremental → marcar leído. Sala única, polling 5 s, badge local y persistencia Oracle. Ver informe específico.
Flujo comercial principal: Lead → Oportunidad → Propuesta → Actividad de seguimiento → Dashboard. Los módulos se comunican por IDs y puertos de consulta, no por navegación de entidades JPA.

Conclusión

Viernes CRM V1 tiene una base sólida para un proyecto académico y un prototipo funcional: módulos bien separados en la intención, una API REST consistente, persistencia Oracle, identidad centralizada y una suite de 257 pruebas en verde. La arquitectura hexagonal por módulo facilita cambiar adaptadores y aislar reglas de negocio.

El principal salto pendiente no es funcional sino operativo: convertir una configuración de desarrollo cómoda en un despliegue seguro y repetible. Eso implica migraciones, secretos externos, un único flujo de autenticación, pruebas de integración/E2E, límites de módulos más estrictos y cierre de las pantallas incompletas.

En una frase: el sistema ya funciona de punta a punta en local; el siguiente hito es endurecerlo para producción sin perder la modularidad que hoy lo hace mantenible.
