¿Qué es una relación N:M y por qué es importante?

📖 Definición técnica

Una relación Muchos-a-Muchos (N:M) es un tipo de asociación entre dos entidades donde múltiples registros de la primera tabla pueden estar relacionados con múltiples registros de la segunda tabla, y viceversa. En bases de datos relacionales, esta relación se implementa mediante una tabla intermedia (también llamada tabla pivote o tabla de unión) que contiene las claves foráneas de ambas tablas principales.

💡
Ejemplo real en Viernes CRM: Una Oportunidad de Venta puede tener asociados múltiples Contactos, y un mismo Contacto puede participar en múltiples Oportunidades. Para modelar esto, se usa la tabla intermedia CRM_OPORTUNIDAD_CONTACTOS.

🔑 ¿Por qué no usar @ManyToMany de JPA?

Viernes CRM no utiliza @ManyToMany de JPA. En su lugar, implementa tablas intermedias como entidades independientes. Esto permite:

  • Agregar atributos extra a la relación (rol, cantidad, esDecisor)
  • Control total sobre cascadas y orphan removal
  • Respetar los límites de módulo (Spring Modulith)
  • Evitar foreign keys físicas entre módulos distintos

🏛️ Principio DDD: Agregados por ID

Siguiendo el patrón Domain-Driven Design, las relaciones entre módulos distintos se manejan por referencia lógica de ID (sin @ManyToOne ni @JoinColumn entre módulos). Cada módulo es dueño de sus propias tablas y consulta los IDs de otros módulos sin generar dependencia física en la base de datos.

2

Estrategia arquitectónica: Agregados DDD por ID

🧩 Patrón de referencia lógica entre módulos

Módulo A (ej: Oportunidades)
Define la entidad principal y la tabla intermedia
↕
Tabla Intermedia (ej: CRM_OPORTUNIDAD_CONTACTOS)
Almacena ID_OPORTUNIDAD + ID_CONTACTO + atributos extra
↕
Módulo B (ej: Clientes/Contactos)
Solo almacena ID como referencia lógica — SIN @JoinColumn
✅
Ventaja clave: Cada módulo es independiente y testeable de forma aislada. El ModularityTests de Spring Modulith valida que no existan dependencias cíclicas.

📐 Reglas de implementación

Regla Implementación en Viernes CRM
FK físicas solo intra-módulo Solo entre tablas del mismo módulo (ej: CRM_CONTACTOS → CRM_CLIENTES)
Referencias lógicas inter-módulo Columna Long idContacto sin @ManyToOne ni @JoinColumn
UniqueConstraint en tabla intermedia Evita duplicados: @UniqueConstraint(columnNames = {"ID_OPORTUNIDAD", "ID_CONTACTO"})
Entidad independiente para la relación Clase @Entity propia con @Id autogenerado y campos extra
Repository propio para la tabla intermedia Cada tabla intermedia tiene su propio JpaRepository

N:M Detallada: Oportunidad ↔ Contactos

N:M Oportunidad — Contactos

Una oportunidad de venta puede involucrar a múltiples contactos del cliente, y un contacto puede participar en múltiples oportunidades. La relación incluye atributos de contexto.

CRM_OPORTUNIDADES
Módulo: oportunidades
◄── N:M ──►
CRM_OPORTUNIDAD_CONTACTOS
Tabla intermedia
rol esDecisor
◄── N:M ──►
CRM_CONTACTOS
Módulo: clientes

📝 Entidad JPA: OportunidadContactoEntity.java

@Entity @Table(name = "CRM_OPORTUNIDAD_CONTACTOS", uniqueConstraints = { @UniqueConstraint(name = "uk_oportunidad_contacto", columnNames = {"ID_OPORTUNIDAD", "ID_CONTACTO"}) }) public class OportunidadContactoEntity { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(name = "ID_OPORTUNIDAD", nullable = false) private Long idOportunidad; // Referencia lógica a CRM_CONTACTOS (módulo clientes), sin foreign key física @Column(name = "ID_CONTACTO", nullable = false) private Long idContacto; @Column(name = "ROL", length = 100) // Atributo extra de la relación private String rol; @Column(name = "ES_DECISOR") // Atributo extra: ¿es el decisor? private Boolean esDecisor = false; @Column(name = "CREADO_EN") // Auditoría temporal private LocalDateTime creadoEn = LocalDateTime.now(); }

Relación 1:N complementaria: Propuesta → Detalles

📋 Diferencia con N:M

La relación entre CRM_PROPUESTAS y CRM_PROPUESTA_DETALLES es una 1:N (un propuesta tiene muchos detalles/líneas de cotización). A diferencia de las N:M, aquí sí se usa @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) porque ambas entidades pertenecen al mismo módulo (propuestas) y los detalles no tienen sentido sin su propuesta padre.

📎 Propuesta → Detalles (1:N con cascade)

CRM_PROPUESTAS
Entidad padre
── 1:N ──►
CRM_PROPUESTA_DETALLES
Líneas de cotización
⚠️
Diferencia clave: En las relaciones N:M del sistema, las tablas intermedias NO usan cascade ni orphanRemoval porque los registros referenciados pertenecen a otros módulos. En la 1:N (Propuesta → Detalles), sí se usa cascade porque todo está dentro del mismo módulo.

Conclusiones y ventajas de la arquitectura

✅ Ventajas del enfoque actual

  • Modularidad real — Cada módulo es independiente y autónomo
  • Atributos extra en la relación (rol, cantidad, esDecisor, orden)
  • No hay foreign keys físicas entre módulos (respeta Spring Modulith)
  • CRUD completo por REST sub-resources
  • UniqueConstraint en todas las tablas intermedias
  • Auditoría temporal con campo creadoEn

📊 Cifras clave

  • 7 relaciones N:M implementadas en el sistema
  • 7 tablas intermedias con entidades JPA independientes
  • 21 tablas Oracle 23c en total (14 maestras + 7 intermedias)
  • 5 módulos involucrados en relaciones N:M
  • 18+ endpoints REST dedicados a gestión de relaciones
  • 0 @ManyToMany JPA — todas implementadas manualmente
🎓
Para la sustentación: La implementación manual de N:M con entidades intermedias demuestra comprensión profunda de modelado relacional, patrones DDD, y arquitectura modular. Es más compleja que usar @ManyToMany de JPA, pero ofrece control total, extensibilidad y respeto por los límites de módulo de Spring Modulith.
