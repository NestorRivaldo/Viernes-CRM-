Cómo se arranca el sistema

🚀 Secuencia de arranque (activar-sistema.bat)

  1. Docker Desktop — Se verifica que Docker esté corriendo
  2. Keycloak — docker compose -f compose-keycloak.yml up -d → Puerto 8180
  3. Oracle 23c — Ya debe estar corriendo como servicio local → Puerto 1521
  4. Backend Spring Boot — mvnw spring-boot:run --spring.profiles.active=dev,keycloak → Puerto 8080
  5. Frontend Angular — npm run start → Puerto 4200

Ciclo de vida de una petición HTTP

🔄 Ejemplo: El usuario crea un nuevo cliente

// PASO 1 — Frontend Angular: El usuario llena el formulario y hace clic en "Guardar" this.http.post('/api/v1/clientes', clienteData, { headers: { 'Authorization': 'Bearer ' + this.keycloak.token } }); // PASO 2 — Spring Security: Intercepta la petición, extrae el JWT SecurityFilterChain → KeycloakJwtAuthenticationConverter → valida firma + roles // PASO 3 — Controller: Recibe la petición ya autenticada @PostMapping public ClienteResponse crear(@Valid @RequestBody ClienteRequest request) // PASO 4 — Service (Use Case): Ejecuta la lógica de negocio ClienteService.crear(request) → valida datos → convierte DTO → dominio // PASO 5 — Adapter de persistencia: Guarda en Oracle ClientePersistenceAdapter.guardar(cliente) → ClienteSpringDataRepository.save() // PASO 6 — Respuesta: Oracle genera el ID, Spring retorna HTTP 201 → ClienteResponse { id: 42, nombre: "Acme Corp", ... }

Cómo funciona la seguridad (RBAC)

🛡️ Flujo de autorización en el backend

Cuando llega una petición HTTP al backend, Spring Security sigue este proceso:

  1. Extrae el token JWT del header Authorization: Bearer ...
  2. Valida la firma del token contra la clave pública de Keycloak
  3. Extrae los roles del claim realm_access.roles del JWT
  4. Verifica la autorización según las reglas definidas en KeycloakSecurityConfig.java
  5. Si el usuario no tiene el rol requerido, Spring devuelve HTTP 403 Forbidden

📝 Reglas de autorización (KeycloakSecurityConfig.java)

// Gestión de usuarios — solo ADMIN .requestMatchers(HttpMethod.POST, "/api/v1/usuarios/**").hasRole("ADMIN") .requestMatchers(HttpMethod.DELETE, "/api/v1/usuarios/**").hasRole("ADMIN") // Transiciones críticas de propuestas — solo ADMIN y JEFE .requestMatchers(HttpMethod.PATCH, "/api/v1/propuestas/*/aprobar").hasAnyRole("ADMIN", "JEFE") .requestMatchers(HttpMethod.PATCH, "/api/v1/propuestas/*/rechazar").hasAnyRole("ADMIN", "JEFE") .requestMatchers(HttpMethod.PATCH, "/api/v1/propuestas/*/cancelar").hasAnyRole("ADMIN", "JEFE") // Eliminación de registros de negocio — solo ADMIN .requestMatchers(HttpMethod.DELETE, ENTIDADES_NEGOCIO).hasRole("ADMIN") // Catálogos — escritura solo ADMIN y JEFE .requestMatchers(HttpMethod.POST, GESTION_COMERCIAL).hasAnyRole("ADMIN", "JEFE") // Todo lo demás — cualquier usuario autenticado .anyRequest().authenticated()

Cuando un VENDEDOR intenta eliminar un cliente:

Cómo funciona el backend Spring Boot

☕ Arquitectura Hexagonal por módulo

Cada módulo de negocio sigue la Arquitectura Hexagonal (Ports & Adapters). La lógica de negocio está aislada en el centro, los adaptadores externos (REST, JPA) se conectan a través de interfaces (puertos).

📥 Puerto de entrada (in)

Interface ManageXxxUseCase que define las operaciones de negocio. El Controller llama a este puerto. Ejemplo:

public interface ManageClienteUseCase { ClienteResponse crear(ClienteRequest req); ClienteResponse actualizar(Long id, ClienteRequest req); List<ClienteResponse> listar(); void eliminar(Long id); }

📤 Puerto de salida (out)

Interface XxxPersistencePort que define las operaciones de persistencia. El Service llama a este puerto. Ejemplo:

public interface ClientePersistencePort { Cliente guardar(Cliente cliente); Optional<Cliente> buscarPorId(Long id); List<Cliente> listarTodos(); void eliminarPorId(Long id); }

🧩 Spring Modulith

El backend usa Spring Modulith para garantizar que los módulos sean independientes. El test ModularityTests verifica que no existan dependencias cíclicas entre módulos y que cada módulo solo acceda a las APIs públicas de otros módulos.

Cómo se persisten los datos en Oracle

🗄️ Flujo de persistencia

  1. Service recibe la entidad de dominio del Use Case
  2. PersistenceAdapter convierte la entidad de dominio a entidad JPA
  3. JpaRepository (Spring Data) ejecuta la operación SQL via Hibernate
  4. Oracle 23c almacena el registro en la tabla correspondiente (CRM_CLIENTES, etc.)
  5. El Adapter convierte la entidad JPA de vuelta a entidad de dominio
  6. El Service retorna el resultado como DTO Response

Cómo funciona la mensajería interna

💬 Arquitectura de la mensajería

  1. El usuario escribe un mensaje en el panel de chat del frontend
  2. Angular envía POST /api/v1/mensajes con el contenido y el JWT
  3. El backend extrae el nombre del usuario del token JWT y guarda el mensaje en CRM_MENSAJES
  4. El frontend hace polling cada 5 segundos con GET /api/v1/mensajes?desde={timestamp}
  5. Los mensajes nuevos aparecen automáticamente en el chat
  6. Un badge de no leídos muestra el conteo de mensajes nuevos en la barra lateral

Cómo funciona el dashboard

📊 Métricas en tiempo real

El dashboard llama a GET /api/v1/dashboard/resumen al cargar. El backend ejecuta queries de conteo (COUNT) sobre las tablas de Oracle y retorna:

  • Total de clientes, leads, oportunidades y propuestas
  • Valor total del pipeline de ventas (SUM de oportunidades)
  • Oportunidades por etapa (para el embudo de ventas)

Adicionalmente, el frontend consulta GET /api/v1/actividades para mostrar las próximas actividades y la actividad reciente — todo con datos reales de Oracle, sin mocks.
