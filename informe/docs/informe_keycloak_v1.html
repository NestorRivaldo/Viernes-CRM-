La autenticación de Viernes CRM V1 ha migrado de un esquema JWT local en base de datos hacia una infraestructura profesional IAM (Identity and Access Management) basada en Keycloak 25.

Esta actualización garantiza desacoplamiento de identidades, cumplimiento del estándar OAuth 2.0 / OpenID Connect (OIDC), inicio de sesión único (SSO), protección contra fuerza bruta y renovación programada de tokens (PKCE S256).

🏗️ 2. Arquitectura y Flujo de Autenticación

Flujo Transaccional:

  1. Autenticación: El cliente Angular se comunica directamente con el endpoint /protocol/openid-connect/token de Keycloak mediante Direct Grant o redirección OIDC.
  2. Emisión de Tokens: Keycloak valida las credenciales y devuelve un access_token firmado criptográficamente que contiene los claims del usuario y sus roles asignados (realm_access.roles).
  3. Consumo de APIs: El frontend adjunta el token en la cabecera Authorization: Bearer <token> en cada llamada REST a través de jwtInterceptor.
  4. Validación Descentralizada: Spring Boot valida la autenticidad del token mediante las llaves públicas expuestas en Keycloak (JWKS /certs) sin realizar consultas a la base de datos de usuarios.

⚙️ 4. Funcionamiento Técnico por Capa

Backend (Spring Boot Resource Server)

  • KeycloakSecurityConfig: Activado únicamente con @Profile("keycloak"). Desactiva CSRF (por ser stateless) y configura CORS permitiendo peticiones desde http://localhost:4200.
  • KeycloakJwtAuthenticationConverter: Extrae los roles del claim realm_access.roles de Keycloak y les añade el prefijo ROLE_ requerido por Spring Security (ej. ROLE_ADMIN).
  • Aislamiento de Perfiles: La clase antigua SecurityConfig y el filtro JwtAuthFilter fueron protegidos con @Profile("!keycloak"), garantizando que no haya conflictos entre ambos sistemas.

Frontend (Angular 22 SPA)

  • AuthService Centralizado: Realiza login contra /openid-connect/token y procesa callbacks SSO con ?code=.... Decodifica el token en memoria para el perfil de usuario.
  • Eliminación de Bypass Demo: Se removió loginSinCredenciales y los datos simulados en dashboard.service.ts. Toda la data ahora proviene de la base de datos Oracle XE.
  • Protección de CORS: trace-id-interceptor.ts fue optimizado para no inyectar cabeceras personalizadas hacia Keycloak, permitiendo preflights limpios.

🚀 5. Guía Paso a Paso para Activar Keycloak

  • Levantar la Infraestructura Docker (Keycloak + DB)
    En la raíz del proyecto (e:\LPII\Viernes), ejecuta: 
    docker compose -f compose-keycloak.yml up -d
    Esto iniciará el contenedor viernes-keycloak (puerto 8180) y viernes-keycloak-db (PostgreSQL en puerto 5433), importando automáticamente el archivo viernes-realm.json.
  • Verificar la Disponibilidad del Servicio
    Abre en el navegador el endpoint de metadatos OpenID para comprobar que el Realm esté activo: 
    http://localhost:8180/realms/viernes-realm/.well-known/openid-configuration
  • Iniciar el Backend con el Perfil Keycloak
    El archivo application.yml ya tiene configurado active: dev,keycloak. Para iniciarlo manualmente: 
    cd viernes-backend
.\mvnw.cmd spring-boot:run
    Spring Boot se conectará a Keycloak y validará cada Bearer token recibido en http://localhost:8080/api/v1/**.
  • Iniciar y Utilizar el Frontend
    En el directorio del frontend: 
    cd viernes-frontend
npx ng serve
    Ingresa a http://localhost:4200/login y autentícate con admin@viernes.com / Admin12345.

🔄 6. Estrategia de Rollback Inmediato

Si en algún momento requieres operar sin Docker o sin Keycloak, el sistema puede revertirse al modo JWT nativo en menos de 1 minuto sin alterar código:

  1. En viernes-backend/src/main/resources/application.yml, cambia active: dev,keycloak a active: dev.
  2. Reinicia el backend. Al no detectar el perfil keycloak, Spring Boot reactivará automáticamente SecurityConfig y JwtAuthFilter.
