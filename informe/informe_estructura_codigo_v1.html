Dos ideas gobiernan todo el backend. Entenderlas es entender el 80% del código.

Idea 2 — Spring Modulith: módulos con fronteras verificadas

Cada módulo es un subpaquete directo de com.viernes con un package-info.java que lo declara. Hay 16 package-info. El tipo controla cuánto puede ver el resto del sistema:

  • OPEN internals accesibles desde otros módulos. Ej.: clientes/package-info.java:1 → @ApplicationModule(type = Type.OPEN). También oportunidades, actividades, propuestas, relationshipmap.
  • CLOSED (por defecto) solo expone su API pública raíz; declara allowedDependencies. Ej.: auth/package-info.java:1 → allowedDependencies = {"usuarios"}. También usuarios, equipos, mensajeria. usuarios solo expone usuarios/UsuariosApi.java:10 + UsuarioResumen.

La regla "un módulo solo llama al Service público de otro, nunca a su Repository/Entity" se verifica sola con src/test/java/com/viernes/ModularityTests.java:12 (ApplicationModules.of(ViernesApplication.class).verify()). Si la violas en un módulo CLOSED, el test falla. shared no tiene package-info propio (raíz abierta); shared/exception y shared/ratelimit son submódulos OPEN.

Regla de oro para modificar: la dependencia siempre apunta hacia adentro (adapters → application → domain). Si necesitas una capacidad nueva, define primero el puerto en application y luego el adapter que lo implementa. Nunca importes un adapter desde application.

06 Anatomía de un módulo (plantilla para agregar)

Si quieres crear un módulo nuevo o entender uno existente, todos siguen el mismo esqueleto. Replica esta estructura y respeta la dirección de dependencia.

com/viernes/<modulo>/ ├─ package-info.java @ApplicationModule(type=OPEN) o allowedDependencies={...} ├─ domain/ │ ├─ <Entidad>.java POJO Lombok, sin JPA │ └─ <Enum / ValueObject>.java ├─ application/ │ ├─ port/in/Manage<Modulo>UseCase.java interfaz: lo que entra │ ├─ port/out/<Modulo>PersistencePort.java interfaz: lo que sale │ ├─ dto/<Modulo>Request/Response.java records o clases Lombok │ └─ service/<Modulo>Service.java implements UseCase, @Transactional └─ adapters/ ├─ in/web/<Modulo>Controller.java @RequestMapping /api/v1/<modulo> └─ out/persistence/ ├─ <Modulo>PersistenceAdapter.java implements PersistencePort ├─ repository/<Modulo>SpringDataRepository.java extends JpaRepository └─ entity/<Modulo>Entity.java @Table CRM_<MODULO>

Pasos para agregar un módulo (checklist)

  1. Crea el paquete com.viernes.<modulo> + package-info.java con @ApplicationModule (OPEN si otros lo usarán libre; CLOSED con allowedDependencies si quieres frontera estricta).
  2. Define domain puro, luego los puertos (in/out) en application, luego el service que implementa el caso de uso.
  3. Implementa los adapters: controller (in/web) y persistencia JPA (out). El mapeo entity↔domain↔DTO es manual (no hay MapStruct activo).
  4. Expón el REST bajo /api/v1/<modulo>; ajusta roles en auth/keycloak/KeycloakSecurityConfig.java si requiere permisos especiales.
  5. En frontend: crea features/<modulo>/ (model, service, list, dialog/form) y registra la ruta lazy en app.routes.ts.
  6. Corre mvnw.cmd test: ModularityTests debe seguir en verde (verifica que no rompiste fronteras).

08 El contrato front ↔ back

Para modificar sin romper, entiende el "acuerdo" entre ambos lados. Si cambias un DTO en el backend, su espejo en el frontend debe cambiar también.

Transporte
REST /api/v1/* + JSON

Frontend resuelve la base con ApiService.buildUrl + environment.apiBaseUrl. No hay proxy dev; el CORS lo resuelve el backend (KeycloakSecurityConfig.java:71, orígenes :4200/:8080).

Auth
Bearer JWT (Keycloak)

El interceptor adjunta el token; el backend lo valida como resource server. Roles ROLE_ADMIN/JEFE/VENDEDOR desde realm_access.roles.

DTOs espejo
*.model.ts ↔ Request/Response

Ej.: clientes.model.ts:57 DocumentoConsultaResponse ↔ record DTO del backend. Campos: nombreCompleto, razonSocial, nombreComercial, estado, condicion, direccion, telefonos.

Errores
body.message → friendlyMessage

El backend devuelve {timestamp,status,error,message,fieldErrors} (GlobalExceptionHandler.java:112); el frontend lo muestra tal cual (jwt.interceptor.ts:119). Por eso un 429/404 se ve inline sin tocar el frontend.

Traza de extremo a extremo: el X-Trace-ID que genera el frontend viaja al backend y aparece en cada log ([traceId], src/main/resources/logback-spring.xml:6). Sirve para correlacionar un clic con sus logs y queries.

11 Ruta de aprendizaje paso a paso

El orden en que conviene leer el código para construir el modelo mental sin abrumarte. De lo simple a lo complejo.

Entrada y configuración
ViernesApplication.java:6 + src/main/resources/application.yml (perfiles dev,keycloak) + application-dev.yml (Oracle, ddl-auto) + application-keycloak.yml. Por qué: saber qué arranca y con qué config.
Un módulo pequeño, completo
productos o etiquetas: recorre domain → port/in → port/out → service → adapter persistence → controller. Por qué: ves el esqueleto hexagonal sin sub-recursos que distraigan.
El flujo de clientes (ya probado)
ClienteController.java → ClienteService.java → puertos → ClientePersistenceAdapter.java y ApisPeruDocumentoAdapter.java. Por qué: integrar persistencia + servicio externo + caché + rate-limit en un solo ejemplo.
Transversal de backend
shared/exception/GlobalExceptionHandler.java + auth/keycloak/KeycloakSecurityConfig.java + shared/cache/CacheConfig.java. Por qué: errores, seguridad y caché aplican a todo lo que modifiques.
Bootstrap y rutas del frontend
app.config.ts:13 + app.routes.ts. Por qué: cómo se monta la SPA, lazy loading y guards.
Sesión y HTTP del frontend
