02 Caché en memoria (Caffeine) — la técnica principal

Idea: guardar en memoria el resultado de lecturas caras para no repetirlas. Spring intercepta los métodos anotados con un proxy AOP: si la clave ya está en caché y vigente, devuelve el valor sin ejecutar el método; si no, lo ejecuta y guarda el resultado.

2.1 Estructura: dónde vive

shared/cache/ ├─ CacheConfig.java @EnableCaching + CaffeineCacheManager (6 cachés, TTL/size/stats) └─ CacheRefreshJob.java @Scheduled: invalida catálogos cada 10 min <módulo>/application/service/ └─ *Service.java @Cacheable (lee) / @CacheEvict (invalida al escribir) clientes/adapters/out/external/ └─ ApisPeruDocumentoAdapter.java @Cacheable positiva + caché negativa manual

2.2 Infraestructura: 6 cachés con TTL diferenciado

El TTL se ajusta al equilibrio frescura vs. costo de cada dato: lo volátil (KPIs) vive poco; lo estable y caro (consulta externa) vive mucho.

maximumSize acota memoria (expulsa al llenarse); expireAfterWrite es el TTL desde la escritura; recordStats() expone hit-ratio para medir. CacheConfig.java:38-67

2.3 Cómo funciona el proxy (mecanismo)

Llamada al método anotado
El proxy de Spring (creado por @EnableCaching, CacheConfig.java:23) intercepta antes de ejecutar el cuerpo.
Evalúa clave y condición
Calcula la clave SpEL (p. ej. #id, 'resumen') y la condition; busca en la caché.
Hit → devuelve sin ejecutar
Si existe y el TTL no venció, retorna el valor guardado: cero consultas a Oracle/APIsPERU.
Miss → ejecuta y guarda
Si no existe, ejecuta el método (va a la BD/API), guarda el resultado con la clave y lo devuelve.

2.5 Lectura + invalidación: @Cacheable / @CacheEvict (etiquetas)

@Transactional(readOnly = true) @Cacheable(cacheNames = "etiquetas", key = "#activa == null ? 'all' : #activa.toString()", condition = "#q == null || #q.isBlank()") // no cachea búsquedas con texto public List<EtiquetaResponse> listar(Boolean activa, String q) { ... } @CacheEvict(cacheNames = "etiquetas", allEntries = true) // invalida al escribir public EtiquetaResponse crear(EtiquetaRequest request) { ... }

Las lecturas se comparten desde memoria; crear/actualizar/archivar vacían la caché (allEntries=true) para que la siguiente lectura recalcule fresco (patrón cache-aside con evaporación en escritura). La condition evita contaminar la caché con búsquedas libres. etiquetas/application/service/EtiquetaService.java:31-59 (igual en fuentes y productos).

2.6 Caché positiva + negativa (integración externa)

@Cacheable(cacheNames = CACHE_DOCUMENTOS, key = "#tipoDocumento.name() + ':' + #numeroDocumento") public DocumentoConsultado consultar(...) { String mensajeNegativo = cacheNegativos.get(clave, String.class); if (mensajeNegativo != null) // ya sabemos que no existe throw new ResourceNotFoundException(mensajeNegativo); // no gasta cuota try { ... } catch (ResourceNotFoundException ex) { cacheNegativos.put(clave, ex.getMessage()); // guarda el "no existe" throw ex; } catch (RestClientResponseException ex) { if (ex.getStatusCode().value() == 404) // solo 404 es negativo real cacheNegativos.put(clave, mensajeError(ex)); throw new IllegalStateException(mensajeError(ex), ex); } }

@Cacheable no cachea excepciones; por eso la caché negativa se maneja manualmente (get/put) para que un reintento de un documento inexistente no vuelva a gastar cuota. Solo el 404 se considera negativo (401/429/5xx son transitorios). clientes/adapters/out/external/ApisPeruDocumentoAdapter.java:50-83

@Scheduled(fixedRateString = "${viernes.cache.refresh-ms:600000}") // 10 min public void refrescarCatalogos() { List.of(CACHE_PRODUCTOS, CACHE_ETIQUETAS, CACHE_FUENTES) .forEach(name -> { Cache c = cacheManager.getCache(name); if (c != null) c.clear(); }); log.info("Cache de catalogos refrescada: {}", caches); }

03 Reducción de llamadas y tráfico

Técnicas que evitan hacer llamadas innecesarias, acotan su costo o traen menos datos por viaje.

3.1 Rate-limit por usuario (protege la cuota externa)

this.contadores = Caffeine.newBuilder() .maximumSize(10_000) .expireAfterWrite(Duration.ofSeconds(ventanaSegundos)) // ventana 60 s .build(); public void verificar(String usuario) { AtomicInteger contador = contadores.get(usuario, clave -> new AtomicInteger()); if (contador.incrementAndGet() > maxConsultas) // máx 20 throw new RateLimitExceededException("Demasiadas consultas...", ventanaSegundos); }

Contador atómico por usuario en una caché Caffeine con ventana deslizante; al superar 20 consultas/60 s lanza 429 con Retry-After. Es por usuario (no por rol) porque cualquier rol registra clientes y usa la consulta. shared/ratelimit/ConsultaDocumentoRateLimiter.java:28-46

3.2 Timeout fail-fast (backend 5 s, frontend 15 s)

SimpleClientHttpRequestFactory f = new SimpleClientHttpRequestFactory(); int timeoutMs = (int) properties.getTimeout().toMillis(); // 5 s f.setConnectTimeout(timeoutMs); // máx para establecer conexión f.setReadTimeout(timeoutMs); // máx esperando respuesta this.restClient = RestClient.builder().baseUrl(...).requestFactory(f).build();

Acota la latencia peor-caso de la llamada externa; al vencer lanza ResourceAccessException → error amigable y el hilo se libera (no se secuestran hilos de Tomcat). En el frontend, timeout(15000) corta la petición si el backend no responde. ApisPeruDocumentoAdapter.java:37-45 · app/core/interceptors/jwt.interceptor.ts:22,36

3.3 Debounce 600 ms (agrupa ráfagas de teclas)

this.form.valueChanges .pipe(debounceTime(600), takeUntilDestroyed(this.destroyRef)) .subscribe((v) => { if (this.form.dirty) this.draft.save(this.draftKey, {...}); });

Espera 600 ms de silencio antes de actuar, evitando una escritura/llamada por cada tecla. Nota honesta: en estos forms alimenta el guardado de borrador (localStorage); la reducción de llamadas a APIsPERU la logran caché + rate-limit + botón. app/features/actividades/actividad-form/actividad-form.ts:136-142 (patrón repetido en ~10 forms).

3.4 Polling incremental + paginación acotada (mensajería)

// frontend: cada 5 s pide solo lo nuevo desde el último id, máx 100 private poll() { const params = new HttpParams().set('despuesDeId', String(this.ultimoId)) .set('limite', String(this.maxMensajes)); this.http.get<MensajeResponse[]>(this.url(), { params }).subscribe(...); } // backend: consulta delta + PageRequest (no trae toda la tabla) public List<Mensaje> findDespuesDeId(Long despuesDeId, int limite) { return repository.findByIdGreaterThanOrderByIdAsc(despuesDeId, PageRequest.of(0, limite))...; }

En vez de recargar todo el chat cada 5 s, trae solo mensajes nuevos acotados a un límite. Reduce payload y trabajo de BD por poll. app/features/mensajeria/mensajeria.service.ts:11,44,144-150 · mensajeria/adapters/out/persistence/MensajePersistenceAdapter.java:29-33

07 Estructura del código de optimización

La optimización está transversal: la infraestructura vive en shared, y las anotaciones se reparten en los services de cada módulo. Así ningún módulo reinventa la caché ni el rate-limit.

viernes-backend/src/main/java/com/viernes/ ├─ shared/ │ ├─ cache/ CacheConfig.java + CacheRefreshJob.java infra caché │ ├─ ratelimit/ ConsultaDocumentoRateLimiter.java infra rate-limit │ ├─ filter/ CorrelationIdFilter.java trazabilidad │ └─ exception/ GlobalExceptionHandler.java 429/404/409 uniformes ├─ dashboard/application/service/ DashboardService.java @Cacheable KPIs ├─ etiquetas|leads|productos/application/service/ @Cacheable + @CacheEvict ├─ clientes/adapters/out/external/ ApisPeruDocumentoAdapter.java caché +/−, timeout └─ mensajeria/adapters/out/persistence/ MensajePersistenceAdapter.java delta + paginación viernes-frontend/src/app/ ├─ core/interceptors/ jwt.interceptor.ts timeout 15 s ├─ core/services/ draft.service.ts borradores └─ features/*/ *-form.ts / mensajeria.service.ts debounce, forkJoin, polling
