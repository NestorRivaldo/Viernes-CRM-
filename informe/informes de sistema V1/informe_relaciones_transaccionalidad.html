🏛️ 1. Paradigma Relacional vs. Hexagonal (Domain-Driven Design)

En un CRM empresarial moderno no todas las conexiones se modelan con llaves foráneas estrictas a nivel de JPA (como @ManyToOne). La arquitectura de Viernes CRM V1 distingue rigurosamente dos categorías de conexiones:

A. Conexiones Físicas Intra-Agregado (JPA Puro)

Se utilizan exclusivamente dentro de la misma raíz de agregado (Aggregate Root). Tienen ciclo de vida dependiente: si el padre se borra, los hijos se borran (CascadeType.ALL y orphanRemoval = true). Son atómicas y gestionadas como una sola unidad por Hibernate.

Ejemplo: Cliente ──> Contactos | Propuesta ──> Detalles

B. Conexiones Lógicas Inter-Módulo (Referencia por ID)

Conectan diferentes módulos de negocio autónomos (p. ej. Actividades con Oportunidades o Propuestas con Clientes). Para evitar acoplamiento rígido, bloqueos distribuidos y problemas de N+1 masivos, se enlazan mediante su ID numérico y se validan en tiempo de ejecución a través de Puertos de Validación (RelacionValidationPort).

Ejemplo: Actividad ──> (idCliente, idLead, idOportunidad, idUsuario)

⚙️ 5. Arquitectura del Sistema Transaccional (@Transactional)

Viernes CRM V1 utiliza el motor transaccional de Spring Framework (JpaTransactionManager) sobre el pool de alto rendimiento HikariCP conectado a Oracle Database 23c. A continuación se detalla cómo opera internamente:

Ciclo de Vida de una Operación Transaccional en Viernes CRM

1
Invocación HTTP y Paso por Seguridad
El cliente Angular envía la petición con el JWT Bearer. El Controller Hexagonal recibe el DTO validado (con @Valid) y delega al puerto de entrada Manage...UseCase.
2
Intercepción del Proxy AOP (@Transactional)
Spring intercepta la llamada mediante un proxy dinámico CGLIB. Si es @Transactional(readOnly = true), instruye a la conexión Hikari/Oracle a modo de solo lectura. Si es mutante, abre una nueva transacción física en Oracle (SET TRANSACTION READ WRITE).
3
Ejecución de Lógica de Dominio y Validaciones
El servicio de aplicación ejecuta las reglas de negocio (p. ej. validación de fechas, recalcular totales de la cotización, validación de existencia cruzada en otros módulos). Las entidades se modifican dentro del Persistence Context de Hibernate.
4
Flush Automático o Rollback por Excepción
Camino Feliz: Al salir exitosamente del método del servicio, Hibernate realiza el flush() automático de los cambios (generando los INSERT/UPDATE/DELETE en Oracle) y Spring emite el COMMIT.
Camino de Error: Si ocurre cualquier excepción no verificada (p. ej. ResourceNotFoundException, IllegalStateException, DataIntegrityViolationException), Spring aborta la transacción emitiendo inmediatamente un ROLLBACK. La base de datos queda intacta y consistente.
5
Cierre de Sesión Estricto (spring.jpa.open-in-view: false)
La sesión de Hibernate se cierra inmediatamente al salir del servicio. La conexión JDBC se devuelve al pool HikariCP antes de que el controlador comience a escribir la respuesta HTTP JSON, previniendo fuga de conexiones y problemas de N+1.

Diferencias Técnicas: @Transactional(readOnly = true) vs @Transactional Mutante

Característica @Transactional(readOnly = true) @Transactional (Escritura / Mutante)
Propósito Consultas, listados, búsquedas y filtros Creación, actualización, cambio de estado, eliminación
Flush Mode Hibernate FlushModeType.COMMIT / MANUAL (No genera SQL de escritura) FlushModeType.AUTO (Sincroniza el contexto antes de queries y al commit)
Dirty Checking (Inspección) Desactivado: Hibernate no crea copias de snapshot en memoria RAM Activado: Detecta campos modificados para generar updates selectivos
Driver JDBC / Oracle 23c Envía señal connection.setReadOnly(true) al pool Sesión de escritura estándar con control de bloqueos de fila (Row Lock)
Segmentos Undo / Rollback Oracle No genera entradas en los segmentos Undo de Oracle Genera registros de redo/undo para garantizar atomicidad y rollback
Impacto de Rendimiento Ahorro del 30-40% en memoria y latencia de CPU Costo computacional compensado por consistencia ACID estricta
✓ Garantía ACID en Viernes CRM V1: En operaciones compuestas como la creación de una propuesta comercial (PropuestaService.crear), el guardado del maestro CRM_PROPUESTAS y de sus CRM_PROPUESTA_DETALLES ocurre dentro de la misma transacción física. Si falla la inserción de un solo ítem, el número de propuesta y la cotización entera se cancelan automáticamente en Oracle (Atomicidad).

🛡️ 7. Conclusiones y Resumen de Buenas Prácticas Aplicadas

Viernes CRM V1 implementa los estándares más rigurosos de la industria en modelado relacional y persistencia empresarial:

1. Desacoplamiento de Módulos (DDD)

Se evitan las redes de llaves foráneas complejas entre módulos independientes. Cada módulo gestiona su propia consistencia y solo se vincula por IDs numéricos validados mediante contratos de puertos.

2. Rendimiento con readOnly = true

El 100% de los métodos de búsqueda y lectura cuentan con readOnly = true, permitiendo a Oracle y Hibernate evitar la sobrecarga de snapshots y bloqueos de fila.

3. Prevención de Fugas (open-in-view: false)

La configuración estricta de JPA garantiza que las conexiones se liberen inmediatamente al terminar la capa de servicio, protegiendo al pool HikariCP bajo alta concurrencia.

4. Inmutabilidad y Snapshots Contractuales

En el módulo de propuestas se aplica desnormalización controlada (clienteNombre) para salvaguardar el valor legal e histórico de las cotizaciones aunque el cliente cambie de razón social.
