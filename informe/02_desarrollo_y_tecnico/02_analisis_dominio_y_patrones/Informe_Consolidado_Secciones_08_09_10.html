08. Análisis del Dominio (DDD)

8.1 Dominio Principal y Subdominios

El dominio principal de Viernes CRM V1 corresponde a la Gestión Comercial CRM y Marketing B2B para el sector corporativo peruano. Sus subdominios se clasifican formalmente en:

Clientes Core Domain com.viernes.clientes Gestión integral de empresas clientes, sus contactos clave y consultas automáticas oficiales a fuentes públicas (RENIEC para DNI, SUNAT para RUC).
Oportunidades Core Domain com.viernes.oportunidades Embudo y pipeline de ventas. Administra el ciclo de vida de cada negociación comercial, cálculo de valor ponderado y vínculos N:M.

8.3 Implementación de Relaciones N:M — Contraste Java vs. Oracle

La implementación descarta el uso de anotaciones @ManyToMany opacas de JPA. En su lugar, cada relación muchos a muchos fue elevada a una entidad intermedia formal con tabla física propia en Oracle, dotándola de identidad y atributos contextuales:

Oportunidades ↔ Contactos OportunidadContacto OportunidadContactoEntity CRM_OPORTUNIDAD_CONTACTOS rol (String), esDecisor (Boolean), Unique(id_oportunidad, id_contacto)
Oportunidades ↔ Productos OportunidadProducto OportunidadProductoEntity CRM_OPORTUNIDAD_PRODUCTOS cantidad (Integer), Unique(id_oportunidad, id_producto)
Oportunidades ↔ Colaboradores OportunidadColaborador OportunidadColaboradorEntity CRM_OPORTUNIDAD_COLABORADORES idUsuario, creadoEn, Unique(id_oportunidad, id_usuario)
Actividades ↔ Participantes ActividadParticipante ActividadParticipanteEntity CRM_ACTIVIDAD_PARTICIPANTES idContacto, creadoEn, Unique(id_actividad, id_contacto)
Actividades ↔ Etiquetas ActividadEtiqueta ActividadEtiquetaEntity CRM_ACTIVIDAD_ETIQUETAS orden (Integer), creadoEn, Unique(id_actividad, id_etiqueta)
Equipos ↔ Usuarios EquipoMiembro EquipoMiembroEntity CRM_EQUIPO_MIEMBROS usuarioId, creadoEn, Unique(equipo_id, usuario_id)
Campañas ↔ Leads CampaniaLead CampaniaLeadEntity CRM_CAMPANIA_LEADS leadId, creadoEn, Unique(campania_id, lead_id)

8.4 Puertos, Servicios y Capa Anticorrupción con Keycloak

La arquitectura hexagonal desacopla completamente el núcleo de negocio mediante puertos de entrada (Manage*UseCase) y puertos de salida (*PersistencePort). El módulo auth actúa como una Capa Anticorrupción (ACL) frente al servidor de identidad externo:

  • KeycloakJwtAuthenticationConverter traduce los roles emitidos en el JWT (claim realm_access.roles) hacia las autoridades de Spring Security (ROLE_ADMIN, ROLE_JEFE, ROLE_VENDEDOR), descartando roles técnicos de Keycloak.
  • El frontend implementa AuthService como una fachada que desacopla los componentes Angular de la librería keycloak-js.
  • El módulo usuarios expone UsuariosApi como Named Interface pública para que otros módulos validen existencia de cuentas sin violar la encapsulación de Spring Modulith.

09. Arquitectura de Software

9.1 Estilo Arquitectónico: Monolito Modular

El backend se estructura como un Monolito Modular gobernado por Spring Modulith 2.0.7 sobre Spring Boot 4.0.7 y Java 21 LTS. La arquitectura modular combina la simplicidad operativa de un único artefacto ejecutable (un único archivo JAR) con la disciplina de límites y aislamiento de responsabilidades propia de los microservicios.

La integridad arquitectónica es verificada automáticamente en tiempo de compilación por la clase de prueba com.viernes.ModularityTests:

class ModularityTests {
    ApplicationModules modules = ApplicationModules.of(ViernesApplication.class);

    @Test
    void verifiesModularStructure() {
        modules.verify(); // Falla si se detectan violaciones de encapsulamiento o dependencias cíclicas
    }
}

9.2 Organización Hexagonal por Módulo

Cada módulo funcional implementa de manera uniforme el patrón de Arquitectura Hexagonal (Puertos y Adaptadores):

com.viernes.<modulo>/
├── domain/                      ← POJOs de dominio y enumeraciones puras (sin JPA)
├── application/
│   ├── dto/                     ← Contratos inmutables de petición y respuesta (Records)
│   ├── port/
│   │   ├── in/                  ← Puertos primarios: Casos de Uso (Manage*UseCase)
│   │   └── out/                 ← Puertos secundarios: Persistencia y validación (*PersistencePort)
│   └── service/                 ← Servicios orquestadores (@Service, @Transactional)
├── adapters/
│   ├── in/web/                  ← Adaptadores primarios: Controladores REST (@RestController)
│   └── out/persistence/         ← Adaptadores secundarios: Implementaciones JPA hacia Oracle
│       ├── entity/              ← Entidades JPA mapeadas a tablas CRM_* (@Entity)
│       └── repository/          ← Repositorios de datos Spring Data JPA
└── package-info.java            ← Metadatos de módulo y reglas de acoplamiento de Spring Modulith

9.4 Decisiones Arquitectónicas (ADRs)

  • ADR-01: Monolito Modular sobre Microservicios: Se adoptó un solo despliegue con Spring Modulith para evitar la sobrecarga de orquestación de red y particionamiento distribuido en un equipo pequeño.
  • ADR-02: Arquitectura Hexagonal Estricta: Desacoplamiento total del dominio respecto a JPA/Oracle. Facilita la creación de pruebas unitarias mediante dobles de prueba (mocks) en los puertos.
  • ADR-03: Keycloak como Resource Server Desacoplado: Flujo Authorization Code con PKCE S256 en la SPA y validación de tokens JWT en el backend sin almacenar sesiones en memoria (arquitectura stateless).
  • ADR-04: Trazabilidad Distribuida con Correlation ID: Inyección del encabezado X-Trace-ID en frontend y propagación en el MDC de Logback para correlacionar eventos entre cliente, backend y logs.

10.3 Patrones GoF Formalmente Declarados como No Identificados

Con el fin de evitar invenciones académicas o clasificaciones forzadas, se declara formalmente que los siguientes 12 patrones GoF no están implementados en el sistema actual:

  • Abstract Factory: No existen familias de productos polimórficos que justifiquen fábricas abstractas.
  • Prototype: No se utiliza clonación de instancias en memoria.
  • Bridge: El desacoplamiento dominio/persistencia se resuelve como Adapter hexagonal.
  • Composite: No existen estructuras en árbol recursivo de parte-todo.
  • Decorator: Las responsabilidades dinámicas se gestionan mediante Proxies de Spring AOP.
  • Flyweight: No se implementa compartición de estado intrínseco en memoria.
  • Command: Los casos de uso se invocan directamente como métodos de servicio, sin encapsularlos en objetos de comando con cola o reversión.
  • Iterator: Se consumen los iteradores estándar del JDK y Streams; no hay un iterador propio del proyecto.
  • Mediator: El acoplamiento entre módulos se gestiona mediante puertos dedicados, sin un mediador centralizado.
  • Memento: No se almacena historial de estados internos para operaciones de deshacer/rehacer.
  • State: Las transiciones de estados en propuestas y leads se implementan mediante enumeraciones y estructuras condicionales (switch/if).
  • Visitor: No hay jerarquías de clases que requieran operaciones visitantes independientes.
